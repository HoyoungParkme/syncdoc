# RFQ: 프로젝트 명세 관리 플랫폼

---

## 1. 배경과 동기

바이브코딩을 하다 보니 **에이전트를 잘 쓰려면 개발자가 PM·AA·SE가 하던 일을 전부 할 줄 알아야 한다**는 걸 느꼈다. 명세가 없으면 에이전트가 구조를 자기 마음대로 정한다.

그래서 명세서를 표준화하고, 정해진 순서대로 명세를 다 쓴 다음에 코딩에 들어가는 방식으로 개발하려 한다. 코딩할 때는 이 명세를 옆에 틀어놓고 보면서 진행한다.

명세를 쓰는 이유는 두 가지다.
1. **에이전트 가이드** — 에이전트가 구조를 임의로 정하지 않고 명세를 따르게 한다.
2. **사람의 가시성** — 사람이 보기 좋게 관리한다.

원래는 팀 협업용 문서 관리 플랫폼으로 시작한 아이디어였고, 위 동기와 합쳐졌다. PM 없이 개발자들끼리 이 흐름으로 프로젝트를 굴릴 예정이다.

## 2. 명세 체인 (11단계)

이 순서로 명세를 쓰고, 마지막에 코딩한다.

| 순서 | 단계 | 비고 |
|---|---|---|
| 1 | RFQ | 고객사 인터뷰 포함 |
| 2 | PRD | 목표/비목표, 요구사항(기능-인수기준, 비기능-성공지표), ID 체계, 미결사항 |
| 3 | 사용자 시나리오 | 페르소나, 시나리오 |
| 4 | USECASE | |
| 5 | 인프라 아키텍처 | |
| 6 | 도메인·클래스·데이터 | 도메인 모델, 클래스 명세, ERD/DD. 원래 ERD는 8번이었으나 클래스와 같은 것을 두 번 그리게 되어 여기로 합침 (PRD 단계에서 수정) |
| 7 | 화면 명세 | 원래 6번에 도메인과 함께 있었으나 독립 단계로 분리 |
| 8 | API 명세 | |
| 9 | SEQUENCE | |
| 10 | MINISPEC | |
| 11 | CODE | |

순서는 **권장이지 강제가 아니다.** 건너뛰는 걸 막지 않는다.

## 3. 요구 사항

#### Q1 문서의 두 가지 버전

모든 명세는 **사람용**과 **에이전트용** 두 버전으로 관리한다.
- 사람은 그림(UML, draw.io 같은 시각 자료)으로 보는 게 좋다.
- 에이전트는 텍스트로 받는 게 좋다.
- **텍스트가 원본이고, 그림은 텍스트에서 자동 생성한다.**

#### Q2 에이전트 연동

- 상위 명세를 주면 하위 명세 초안을 에이전트가 만든다. (RFQ → PRD 초안, PRD → 시나리오 초안 …)
- 팀원마다 쓰는 에이전트(Claude Code, Cursor 등)가 다르다. **특정 에이전트 툴에 종속되면 안 된다.**
- 에이전트에게 명세를 전달하는 구체적 방식(파일 / MCP)은 RFQ에서 정하지 않는다. → PRD

#### Q3 플랫폼 기능 (1차 인터뷰에서 확정)

| 기능 | 설명 |
|---|---|
| ID 기반 상호참조 | 문서·항목 간 참조 연결 |
| 변경 추적 | 상위가 바뀌면 하위에 영향 표시 |
| 버전 관리 | 변경 이력 보존, 비교 |
| 공통 포맷 | 텍스트(MD) 원본, HTML은 렌더링 |
| 스토리지 | 문서 저장 위치·방식 |
| 단계별 상태 | 초안 / 검토 / 승인 등 |
| 댓글·리뷰 | 문서 위에서 검토 |
| 프로젝트 대시보드 | 프로젝트별 진행 모니터링 |

#### Q4 코딩 중 사용

코딩할 때 명세를 옆에 열어놓고 참조하며 진행한다. 열람이 목적이며, 별도의 체크리스트 기능을 요구하는 것은 아니다.

#### Q5 기존 문서

팀 문서가 너무 방대해서 정리가 안 된 상태다. 앞으로의 문서는 이 플랫폼에서 쓴다. 기존 문서 이관은 요구하지 않는다.

## 4. 사용자와 환경

| 항목 | 내용 |
|---|---|
| 사용 범위 | 사내 누구나 쓸 수 있게. 폐쇄망 아님 |
| 실사용 인원 | 2~3명 |
| 배포 | 별도 배포 없음. 요청자 노트북에서 서버를 띄우고 같은 네트워크 대역의 사용자가 접속 |
| 코드 저장소 | GitHub |
| 개발 주체 | 요청자 본인이 에이전트로 바이브코딩 |
| 기한 | 없음 |

## 5. 이 플랫폼의 첫 프로젝트

이 플랫폼 자체를 위 11단계 체인으로 만든다. 지금 쓰고 있는 RFQ·PRD·사용자 시나리오·USECASE가 첫 번째 프로젝트의 산출물이 된다.

## 6. 미정 / 다음 단계로 넘기는 것

- 서비스 이름
- 에이전트에게 명세를 전달하는 방식 (파일 / MCP / 둘 다)
- 사람용 그림 생성 범위 (mermaid 렌더링으로 충분한지, draw.io 수준이 필요한지)
- 기술 스택
- 단계별 상태·리뷰·승인 기능의 우선순위 (실사용 2~3명이라 얼마나 필요한지)
