# RFQ: 프로젝트 명세 관리 플랫폼

---

## 1. 배경과 동기

바이브코딩을 하다 보니 **에이전트를 잘 쓰려면 개발자가 PM·AA·SE가 하던 일을 전부 할 줄 알아야 한다**는 걸 느꼈다. 명세가 없으면 에이전트가 구조를 자기 마음대로 정한다.

그래서 명세서를 표준화하고, 정해진 순서대로 명세를 다 쓴 다음에 코딩에 들어가는 방식으로 개발하려 한다. 코딩할 때는 이 명세를 옆에 틀어놓고 보면서 진행한다.

명세를 쓰는 이유는 두 가지다.
1. **에이전트 가이드** — 에이전트가 구조를 임의로 정하지 않고 명세를 따르게 한다.
2. **사람의 가시성** — 사람이 보기 좋게 관리한다.

원래는 팀 협업용 문서 관리 플랫폼으로 시작한 아이디어였고, 위 동기와 합쳐졌다. PM 없이 개발자들끼리 이 흐름으로 프로젝트를 굴릴 예정이다.

## 2. 명세 체인 (11단계)

이 순서로 명세를 쓰고, 마지막에 코딩한다.

| 순서 | 단계 | 비고 |
|---|---|---|
| 1 | RFQ | 고객사 인터뷰 포함 |
| 2 | PRD | 목표/비목표, 요구사항(기능-인수기준, 비기능-성공지표), ID 체계, 미결사항 |
| 3 | 사용자 시나리오 | 페르소나, 시나리오 |
| 4 | USECASE | |
| 5 | 인프라 아키텍처 | |
| 6 | 도메인·클래스·데이터 | 도메인 모델, 클래스 명세, ERD/DD. 원래 ERD는 8번이었으나 클래스와 같은 것을 두 번 그리게 되어 여기로 합침 (PRD 단계에서 수정). **셋을 한 번에 쓰지 않는다** — 도메인 모델은 여기서, 클래스 명세는 8 API 뒤에 돌아와서, ERD는 그 뒤. 합친 건 그림이 같아서지 순서가 같아서가 아니다 |
| 7 | 화면 명세 | 원래 6번에 도메인과 함께 있었으나 독립 단계로 분리 |
| 8 | API 명세 | |
| 9 | SEQUENCE | |
| 10 | MINISPEC | |
| 11 | CODE | |

순서는 **권장이지 강제가 아니다.** 건너뛰는 걸 막지 않는다.

## 3. 요구 사항

#### Q1 문서의 두 가지 버전

모든 명세는 **사람용**과 **에이전트용** 두 버전으로 관리한다.
- 사람은 그림(UML, draw.io 같은 시각 자료)으로 보는 게 좋다.
- 에이전트는 텍스트로 받는 게 좋다.
- **텍스트가 원본이고, 그림은 텍스트에서 자동 생성한다.**

#### Q2 에이전트 연동

- 상위 명세를 주면 하위 명세 초안을 에이전트가 만든다. (RFQ → PRD 초안, PRD → 시나리오 초안 …)
- 팀원마다 쓰는 에이전트(Claude Code, Cursor 등)가 다르다. **특정 에이전트 툴에 종속되면 안 된다.**
- 에이전트에게 명세를 전달하는 구체적 방식(파일 / MCP)은 RFQ에서 정하지 않는다. → PRD

#### Q3 플랫폼 기능 (1차 인터뷰에서 확정)

| 기능 | 설명 |
|---|---|
| ID 기반 상호참조 | 문서·항목 간 참조 연결 |
| 변경 추적 | 상위가 바뀌면 하위에 영향 표시 |
| 버전 관리 | 변경 이력 보존, 비교 |
| 공통 포맷 | 텍스트(MD) 원본, HTML은 렌더링 |
| 스토리지 | 문서 저장 위치·방식 |
| 단계별 상태 | 초안 / 검토 / 승인 등 |
| 댓글·리뷰 | 문서 위에서 검토 |
| 프로젝트 대시보드 | 프로젝트별 진행 모니터링 |

#### Q4 코딩 중 사용

코딩할 때 명세를 옆에 열어놓고 참조하며 진행한다. 열람이 목적이며, 별도의 체크리스트 기능을 요구하는 것은 아니다.

#### Q5 기존 문서

팀 문서가 너무 방대해서 정리가 안 된 상태다. 앞으로의 문서는 이 플랫폼에서 쓴다. 기존 문서 이관은 요구하지 않는다.

## 4. 사용자와 환경

| 항목 | 내용 |
|---|---|
| 사용 범위 | 사내 누구나 쓸 수 있게. 처음엔 폐쇄망이 아니었다 — 써 본 뒤 폐쇄망에서도 쓰게 됐다(8장) |
| 실사용 인원 | 2~3명 — 써 본 뒤 「한 사람이 프로젝트 하나를 다 쓴다」로 바뀌었다(7장) |
| 배포 | 별도 배포 없음. 요청자 노트북에서 서버를 띄우고 같은 네트워크 대역의 사용자가 접속 |
| 코드 저장소 | GitHub — 써 본 뒤 GitHub 없이 싱크독 서버에 바로 저장하는 길이 더해졌다. 프로젝트마다 고른다(8장) |
| 개발 주체 | 요청자 본인이 에이전트로 바이브코딩 |
| 기한 | 없음 |

## 5. 이 플랫폼의 첫 프로젝트

이 플랫폼 자체를 위 11단계 체인으로 만든다. 지금 쓰고 있는 RFQ·PRD·사용자 시나리오·USECASE가 첫 번째 프로젝트의 산출물이 된다.

## 6. 미정 / 다음 단계로 넘기는 것

- 서비스 이름
- 에이전트에게 명세를 전달하는 방식 (파일 / MCP / 둘 다)
- 사람용 그림 생성 범위 (mermaid 렌더링으로 충분한지, draw.io 수준이 필요한지)
- 기술 스택
- 단계별 상태·리뷰·승인 기능의 우선순위 (실사용 2~3명이라 얼마나 필요한지) → 7장에서 답이 나왔다
- 폐쇄망 버전(8장 Q7의 1) → 8장에서 답이 나왔다 — 브랜치를 나누지 않고 코드 하나에 판을 설정으로 가른다

## 7. 써 본 뒤 (2026-09-21)

첫 프로젝트(싱크독 자신)와 프로젝트 일곱 개를 더 굴려 본 뒤 요청자가 말한 것이다. 인터뷰가 아니라 사용 소감이며, 그대로 적는다.

#### Q6 써 본 결과

1. "계정별로 프로젝트 관리가 안 되어 있음."
2. "화면 명세를 클로드가 와이어프레임으로 주는데 이거 그대로 올리면 좋겠음. 지금은 이상한 구조만 올라감."
3. "여러 명이 같이 개발한다고 승인 이런 걸 만들었지만, 그냥 한 사람이 하나의 프로젝트를 다 명세를 쓴다. 이런 식으로 가는 게 좋을 듯."
4. "끊어진 참조 이런 것들, 읽기가 어렵고 사용이 어려움."

**결정 — 아예 1인 도구로 전환한다.** 승인·리뷰·전파 같은 협업 장치는 걷어내고, 프로젝트는 등록한 사람의 것으로 가른다. 6장의 마지막 미정(상태·리뷰·승인의 우선순위)은 이것으로 닫혔다 — 상태는 남기되 리뷰와 승인은 필요 없다.

## 8. 써 본 뒤 — 둘째 (2026-09-30)

싱크독으로 명세를 쓰고 그대로 코딩까지 해 본 사용자가 준 피드백이다. 7장과 같이 소감이며, 그대로 적는다.

#### Q7 두 번째 피드백

1. "폐쇄망 환경에서 가능하도록 폐쇄망 버전 생성 — 깃허브를 이용하지 않고 바로 서버에 저장하는 식으로 사용하게. 그럼 처음에 싱크독 MCP 연결해서 사용할 때 깃허브로 쓸 건지, 폐쇄망에서 쓸 건지 확인하는 절차가 필요한데 자세한 계획을 세워야 함."
2. "graphify를 이용한 코드 탐지 — 실제로 코드가 구현되고 명세서 기반으로 확인을 할 때 graphify를 이용해서 실제로 기능을 대충 어림잡아서 보는 게 아닌 graph로 연결을 해서 직접 자세하게 비교하는 방식 필요. 이걸 웹에서도 확인해서 웹에 있는 챗봇도 연결을 하면 더 풍성한 답변을 기대할 수 있음."
3. "글 가시성 — 글에서 이 가시성이 떨어지는 이유가 글의 줄바꿈의 문제가 있는 듯함." 요청자가 덧붙였다 — 채팅에서도 적용하고, 채팅 답은 한 번에 나오지 말고 흘러 나오게.

**처리** — 3은 화면 규칙이라 요구사항을 늘리지 않고 카드 AV(어절 단위 줄바꿈)·AW(답 스트리밍)로 닫았다. 2는 [[SYNC-PRD-001#R13]]이 되었다. 1은 [[SYNC-PRD-001#R14]](서버 저장)와 [[SYNC-PRD-001#R15]](폐쇄망판)가 되었다. 2026-09-30 요청자와 정한 것 — 브랜치를 나누지 않고 코드 하나에 판을 설정으로 가르며 릴리즈만 따로 만든다(인터넷판·폐쇄망판). GitHub로 쓸지 서버에 저장할지는 프로젝트를 만들 때 고르고, 둘 다 켜진 서버에서는 에이전트가 사람에게 먼저 묻는다 — 요청자가 말한 「처음 연결해 쓸 때 확인하는 절차」다. 폐쇄망판은 요청자 혼자 쓰고 로그인이 없다 — 인터넷 없이 돌고, 저장은 서버만이며, 이미지 묶음으로 들여간다.

## 9. 써 본 뒤 — 셋째 (2026-10-06)

요청자가 저장소 공개 범위와 폐쇄망 작업을 다시 잡으며 한 말이다. 그대로 적는다. 계기가 된 보안 사고의 경위는 이 저장소가 공개라 적지 않는다(#310·#320과 같다).

#### Q8 비공개 저장소와 두 릴리즈

1. "이거 내가 public을 고집한건 하나의 깃허브의 하나의 private만 넣을 수 있는줄 알았어. 그래서 일부로 private을 지원 안하게 한거야. 이제 private도 지원하게해줘. 공개로 올라가는건 상관없게 하자."
2. "단 예전처럼 보안 이슈가 있는 경우도 있을거야. 이런경우에 대해서도 생각을 해봐야돼. 폐쇄망에서 작업하는거자나. 이런경우는 싱크독 로컬 버전을 불러오게 해야겠어. 릴리즈를 다르게 하자. 기존에 쓰던건 싱크독_깃허브 mcp, 이번에 로컬에서만 이뤄지게 할거(깃허브 업로드 X)는 싱크독_로컬로 계획해서 설계하고 작업을 진행하자."
3. "이건 프로그램으로 만들어서 exe로 설치해서 썼으면해. 속도면에서 rust로 해도 될듯"

**처리** — 1은 [[SYNC-CODE-001#BS]](새 저장소의 공개 여부를 만들 때 고른다, 고르지 않으면 비공개)로 닫았다. v1의 「공개 저장소만」은 이 오해에서 나왔다. 서버 저장으로 옮겼던 프로젝트는 [[SYNC-CODE-001#BT]]로 GitHub에 되돌렸다. 2는 릴리즈 이름이 되었다 — 인터넷판이 **싱크독_깃허브**, 폐쇄망판이 **싱크독_로컬**이다([[SYNC-PRD-001#R15]], [[SYNC-CODE-001#BU]]). 판을 가르는 설정(`EDITION`)은 그대로고 화면·MCP 서버 이름(`syncdoc_github`·`syncdoc_local`)·반입 묶음이 이름을 말한다. 한 PC에서 둘을 나란히 띄운다. 3은 2026-10-06 요청자와 정한 것이다 — 싱크독_로컬을 Rust로 새로 만들고, 첫 판부터 싱크독_깃허브와 같은 기능(GitHub 빼고), 윈도·리눅스, 같은 저장소·같은 명세. 그때까지는 지금의 Docker 폐쇄망판을 싱크독_로컬 이름으로 쓴다. 8장의 「코드 하나에 판을 설정으로」는 그 설계 단계에서 다시 쓴다.
