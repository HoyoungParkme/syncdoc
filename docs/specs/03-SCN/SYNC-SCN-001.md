# 사용자 시나리오: 싱크독 (SyncDoc)

---

## 0. 범위와 전제

이 문서의 주체는 **사람**이다. 에이전트는 사람이 목적을 이루기 위해 쓰는 수단으로 등장하며, 시스템과 직접 주고받는 액터로서의 에이전트는 USECASE에서 다룬다.

**작업의 진입점은 싱크독이 아니라 평소 쓰던 에이전트다.** 사람은 하던 대로 자기 툴에서 에이전트와 대화하고, 결정된 내용이 MCP를 통해 싱크독에 남는다. 싱크독 웹은 읽고, 확정하고, 검토하는 곳이다.

```
평소 작업:  사람 ↔ 에이전트 (Claude Code / Codex / Gemini)
                    ↕ MCP
              싱크독 서버 ── 웹: 읽기·그림·대시보드·확정·댓글
                    ↕
              코드 저장소 docs/specs/ (명세 원본)
```

---

## 1. 페르소나

### P1 박호영

- 디포커스 AI팀 개발자. 싱크독을 만들었고 자기 프로젝트에도 쓴다.
- 쓰는 에이전트 툴은 Claude Code.
- **겪는 문제**: 명세 없이 에이전트한테 맡기면 구조를 제멋대로 정한다. 대화하면서 결정한 것들이 채팅 기록에만 남고 사라진다.
- **원하는 것**: 대화하다가 결정된 게 자동으로 명세로 쌓이고, 그 명세를 에이전트가 다시 읽고 따르는 것.

### P2 김민준

- 같은 팀 개발자. 호영과 같은 프로젝트에 참여한다.
- 쓰는 에이전트 툴이 호영과 다르다 (Codex, Gemini 등).
- **겪는 문제**: 호영이 잡아놓은 설계를 알아야 하는데 물어보는 것 말고 방법이 없다. 자기 에이전트한테 같은 맥락을 매번 다시 설명한다.
- **원하는 것**: 툴이 달라도 같은 명세를 보고, 자기도 명세를 고칠 수 있는 것.

두 사람은 대등하다. 둘 다 명세를 쓰고 서로 검토하고 확정한다. PM은 없다. 권한 구분도 없다.

## 2. 시나리오

### S1 대화하다가 명세가 쌓인다 (최우선)

**주체**: 박호영
**상황**: 새 프로젝트를 시작한다. 평소처럼 Claude Code를 열었다.

1. 저장소를 하나 만들고, 에이전트한테 "이 저장소로 싱크독 시작해줘"라고 한다. 에이전트가 MCP 초기화 도구를 부른다. `docs/specs/` 아래 11단계 디렉터리와 템플릿 껍데기가 커밋된다.
2. 만들려는 것에 대해 에이전트와 대화한다. 배경, 원하는 것, 안 할 것을 주고받으며 정리한다.
3. 어느 정도 정리되면 "지금까지 나온 걸로 RFQ 써줘"라고 한다. 에이전트가 MCP로 RFQ 문서를 만든다. 템플릿 규약대로 frontmatter가 채워지고 항목마다 `#Q01` 같은 ID가 붙는다. `초안` 상태로 첫 버전이 생기고 커밋된다.
4. 이어서 PRD로 넘어간다. 에이전트가 방금 쓴 RFQ를 MCP로 읽고, 호영과 대화하며 목표·요구사항을 정한다. 본문에 `[[SYNC-RFQ-001#Q01]]` 참조가 들어간다.
5. 대화 중 앞 단계 결정이 바뀐다. 에이전트가 RFQ를 수정하고, 그 항목을 참조하던 PRD 항목에 `확인 필요` 플래그가 붙는다.
6. 3~5를 사용자 시나리오 → USECASE → 인프라 → … → MINISPEC까지 반복한다. 흐름은 계속 대화이고, 싱크독은 그 결과를 받아 쌓는다.
7. 대시보드를 열어 11단계가 다 채워진 걸 확인한다.

**변형 — 순서를 건너뛴다**: 인프라 아키텍처를 안 썼는데 API 명세부터 쓴다. 싱크독은 막지 않는다. 대시보드에 인프라가 `미작성`으로 남을 뿐이다.

**성공 조건**: 평소 작업 흐름을 바꾸지 않았는데 11단계 명세가 남아 있다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R5]], [[SYNC-PRD-001#R9]]

### S2 명세를 읽고 확정한다

**주체**: 박호영, 김민준
**상황**: 에이전트가 써놓은 PRD를 사람이 확인할 차례다.

1. 호영이 싱크독 웹에서 PRD를 연다. 사람용 뷰라 참조가 클릭 링크로 보이고, 클릭하면 RFQ의 해당 항목으로 간다.
2. 한 요구사항이 애매하다. 그 줄에 댓글을 단다.
3. 민준이 댓글을 보고 답글을 단다. 상태가 `초안`이라 아직 확정 전인 걸 안다.
4. 호영이 Claude Code에서 "PRD R3 문단 이렇게 고쳐줘"라고 한다. 에이전트가 MCP로 수정한다. 새 버전이 생기고 커밋된다.
5. 댓글을 "해결됨" 처리한다.
6. 둘이 대화로 "이제 확정하죠" 합의하고, 호영이 상태를 `승인`으로 바꾼다.
7. 이후 MCP로 이 문서를 받는 에이전트는 상태가 `승인`인 걸 보고 확정 명세로 다룬다.

**변형 — 확정 후 수정**: 승인된 PRD를 나중에 고치면 자동으로 `검토중`으로 내려간다. 에이전트가 다시 받으면 확정이 아님을 알게 된다.

**변형 — 동시 수정**: 호영의 에이전트와 민준의 에이전트가 같은 문서를 거의 동시에 수정하려 한다. 늦은 쪽이 들고 있던 버전이 낡았으므로 쓰기가 거부되고 현재 버전과 내용이 돌아온다. 그 에이전트는 그걸 읽고 다시 판단한다.

**성공 조건**: 에이전트가 초안과 확정 명세를 구분한다. 사람과 에이전트가 같은 문서를 고쳐도 덮어쓰지 않는다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R6]], [[SYNC-PRD-001#R7]], [[SYNC-PRD-001#R9]]

### S3 코딩하면서 명세를 본다 (차순위)

**주체**: 박호영
**상황**: MINISPEC까지 다 나왔고 이제 구현한다.

1. 화면 한쪽에 싱크독을 띄운다. MINISPEC을 사람용 뷰로 열어두고 본다.
2. 다른 쪽 Claude Code에서 "MINISPEC 3번 구현해줘"라고 시킨다. 명세와 코드가 같은 저장소에 있으므로 에이전트는 clone된 파일로도, MCP로도 접근할 수 있다.
3. 에이전트가 해당 문서를 받는다. 상태가 `승인`인 걸 확인한다.
4. 본문에서 `[[SYNC-API-001#POST/orders]]` 참조를 발견하고 그 항목을 다시 요청해 읽는다. 필요하면 ERD 테이블 정의까지 따라간다.
5. 명세대로 코드가 나온다. 호영은 싱크독 화면의 명세와 결과를 대조한다.
6. 구현한 커밋 URL을 MINISPEC 항목에 코드 링크로 붙인다.

**변형 — 명세가 틀렸다**: 구현하다 보니 API 명세의 응답 필드가 ERD에 없다. 에이전트한테 시켜 API 명세를 고친다. 상태가 `검토중`으로 내려가고, 이 항목을 참조하던 MINISPEC에 `확인 필요` 플래그가 붙는다.

**성공 조건**: 에이전트가 구조를 임의로 정하지 않고 명세를 따른다.
**연관 요구사항**: [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R5]], [[SYNC-PRD-001#R6]], [[SYNC-PRD-001#R9]]

### S4 상위 명세가 바뀐다

**주체**: 박호영, 김민준
**상황**: 요구사항 하나가 바뀌어 아래로 영향이 번진다.

1. 호영이 에이전트에게 PRD의 `#R12`를 고치게 한다. 에이전트가 MCP로 저장한다.
2. 싱크독이 하위 항목 4개를 찾아 "전파 미결정"으로 남긴다. 호영의 내 할 일에 뜬다.
3. 호영이 내 할 일에서 열어 "예"를 누른다. USECASE·API·ERD·MINISPEC의 해당 항목에 `확인 필요` 플래그가 붙는다.
4. 민준의 "내 할 일"에 자기 담당 항목 2건이 뜬다.
5. 항목을 연다. R12의 변경 전/후 diff가 위에, 자기 항목이 아래에 나란히 보인다.
6. 에이전트에게 API 명세를 고치게 한 뒤 "확인함"을 누른다. ERD는 영향 없다고 판단해 수정 없이 "확인함"만 누른다.
7. 누가 언제 확인했는지 이력에 남는다.

**변형 — 오탈자**: 오타만 고쳤으면 3번에서 "하위 전파 안 함"을 고른다. 사유가 이력에 남는다.

**변형 — 하위에서 결정이 바뀜**: 민준이 API 명세를 쓰다가 "저장할 때 바뀐 항목을 에이전트가 지정하자"고 정했다. 유스케이스 UC-A6는 여전히 "시스템이 diff로 찾는다"라고 되어 있다. 민준의 에이전트가 API 명세를 저장하면서 "UC-A6와 어긋남"을 지정한다 → UC-A6에 `하위 불일치` 플래그가 붙고 호영의 내 할 일에 뜬다. 에이전트가 몰랐다면, 민준이 API 명세를 승인할 때 상위 항목 목록에서 UC-A6를 "어긋남"으로 체크해 같은 플래그를 만든다.

**변형 — 항목 삭제**: 요구사항이 아예 빠지면 하위 항목에 `끊어진 참조` 플래그가 붙는다. 담당자가 참조를 바꾸거나 항목을 같이 지운다.

**성공 조건**: 낡은 명세를 보고 개발하는 일이 없다.
**연관 요구사항**: [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R4]], [[SYNC-PRD-001#R8]]

### S5 다른 툴을 쓰는 팀원이 합류한다 (차순위)

**주체**: 김민준
**상황**: 민준은 호영과 다른 에이전트 툴을 쓴다.

1. 민준이 자기 툴(Codex 또는 Gemini)에서 싱크독 MCP에 연결한다.
2. "SYNC 프로젝트 문서 목록 보여줘"라고 시킨다. 11단계 문서와 각 상태가 온다.
3. 승인된 API 명세를 받아서 그걸 근거로 자기 담당 부분을 구현한다. 호영한테 맥락을 물을 필요가 없다.
4. 구현하다 보니 명세에 빠진 게 보인다. 에이전트한테 시켜 MCP로 API 명세에 항목을 추가한다.
5. 추가된 내용은 사람이 쓴 것과 똑같이 새 버전이 되고, 참조가 추출되고, 변경 전파가 돈다. 작성 주체는 에이전트로 기록된다.
6. 문서 상태가 `검토중`으로 내려간다. 호영이 웹에서 보고 확정 여부를 판단한다.

**성공 조건**: 툴이 달라도 같은 명세를 읽고 쓴다. 누가·무엇으로 썼는지 추적된다.
**연관 요구사항**: [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R6]], [[SYNC-PRD-001#R9]]

### S6 명세를 사람 눈으로 훑어본다

**주체**: 박호영, 김민준
**상황**: 설계 전체를 파악하거나 남에게 설명해야 한다.

1. 프로젝트 상세에서 "순서대로 읽기"를 연다. RFQ부터 MINISPEC까지 이어서 읽는다.
2. 시퀀스 다이어그램 단계에 오면 mermaid 코드가 아니라 그림으로 보인다. ERD도 마찬가지다.
3. 원본 탭으로 바꾸면 에이전트가 읽는 MD 그대로가 보인다. 필요하면 복사해 에이전트에게 붙여넣는다.
4. 참조 그래프를 열어 어느 요구사항이 어디까지 이어졌는지 본다. 참조가 하나도 없는 항목이 눈에 띈다.
5. 대시보드에서 `확인 필요` 플래그가 며칠째 남아 있는 걸 발견하고 처리한다.

**성공 조건**: 사람이 설계 전체를 그림과 흐름으로 파악한다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R8]], [[SYNC-PRD-001#R10]]

### S7 플랫폼 없이 명세에 접근한다

**주체**: 박호영, 김민준
**상황**: 호영의 노트북이 꺼져 있어 싱크독 서버가 안 돈다.

1. 민준이 저장소를 clone한다. 명세가 `docs/specs/`에 코드와 함께 들어 있다.
2. 원본 MD를 그대로 읽는다. frontmatter에 상태가 있고, `[[]]` 참조로 어느 문서를 봐야 하는지 알 수 있다. 에이전트도 파일로 읽으면 된다.
3. 필요하면 로컬에서 MD를 고치고 push한다.
4. 나중에 싱크독 서버가 켜지면 그 커밋을 새 버전으로 인식하고, 참조 추출과 변경 전파를 돌린다.

**성공 조건**: 플랫폼이 죽어도 명세가 잠기지 않는다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R5]]
