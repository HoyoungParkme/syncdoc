# 사용자 시나리오: 싱크독 (SyncDoc)

---

## 0. 범위와 전제

이 문서의 주체는 **사람**이다. 에이전트는 사람이 목적을 이루기 위해 쓰는 수단으로 등장하며, 시스템과 직접 주고받는 액터로서의 에이전트는 USECASE에서 다룬다.

**작업의 진입점은 싱크독이 아니라 평소 쓰던 에이전트다.** 사람은 하던 대로 자기 툴에서 에이전트와 대화하고, 결정된 내용이 MCP를 통해 싱크독에 남는다. 싱크독 웹은 읽고, 완료로 올리는 곳이다.

```
평소 작업:  사람 ↔ 에이전트 (Claude Code / Codex / Gemini)
                    ↕ MCP
              싱크독 서버 ── 웹: 읽기·그림·대시보드·완료 표시
                    ↕
              코드 저장소 docs/specs/ (명세 원본)
```

---

## 1. 페르소나

### P1 박호영

- 디포커스 AI팀 개발자. 싱크독을 만들었고 자기 프로젝트에도 쓴다.
- 쓰는 에이전트 툴은 Claude Code.
- **겪는 문제**: 명세 없이 에이전트한테 맡기면 구조를 제멋대로 정한다. 대화하면서 결정한 것들이 채팅 기록에만 남고 사라진다.
- **원하는 것**: 대화하다가 결정된 게 자동으로 명세로 쌓이고, 그 명세를 에이전트가 다시 읽고 따르는 것.

### P2 김민준

- 다른 팀 개발자. 호영과 **다른 프로젝트**를 혼자 굴린다. 같은 싱크독 서버를 쓴다.
- 쓰는 에이전트 툴이 호영과 다르다 (Codex, Gemini 등).
- **겪는 문제**: 툴이 다르면 명세를 넘기는 방식이 제각각이다. 자기 에이전트한테 같은 맥락을 매번 다시 설명한다.
- **원하는 것**: 툴이 달라도 같은 방식으로 명세를 쓰고 읽는 것. 자기 프로젝트만 보이는 것.

두 사람은 각자 자기 프로젝트를 쓴다. 한 프로젝트를 나눠 쓰지 않는다 — 써 보니 그랬다([[SYNC-PRD-001#G7]]). PM은 없다. 권한 구분도 없다.

## 2. 시나리오

### S1 대화하다가 명세가 쌓인다 (최우선)

**주체**: 박호영
**상황**: 새 프로젝트를 시작한다. 평소처럼 Claude Code를 열었다.

1. 저장소를 하나 만들고, 에이전트한테 "이 저장소로 싱크독 시작해줘"라고 한다. 에이전트가 MCP 초기화 도구를 부른다. `docs/specs/` 아래 11단계 디렉터리와 템플릿 껍데기가 커밋된다.
2. 만들려는 것에 대해 에이전트와 대화한다. 배경, 원하는 것, 안 할 것을 주고받으며 정리한다.
3. 어느 정도 정리되면 "지금까지 나온 걸로 RFQ 써줘"라고 한다. 에이전트가 MCP로 RFQ 문서를 만든다. 템플릿 규약대로 frontmatter가 채워지고 항목마다 `#Q01` 같은 ID가 붙는다. `초안` 상태로 첫 버전이 생기고 커밋된다.
4. 이어서 PRD로 넘어간다. 에이전트가 방금 쓴 RFQ를 MCP로 읽고, 호영과 대화하며 목표·요구사항을 정한다. 본문에 `[[SYNC-RFQ-001#Q01]]` 참조가 들어간다.
5. 대화 중 앞 단계 결정이 바뀐다. 에이전트가 RFQ를 수정한다. 항목을 아예 뺐다면 그것을 참조하던 PRD 항목에 `끊어진 참조`가 표시되어 호영이 따라가 고친다.
6. 3~5를 사용자 시나리오 → USECASE → 인프라 → … → MINISPEC까지 반복한다. 흐름은 계속 대화이고, 싱크독은 그 결과를 받아 쌓는다.
7. 대시보드를 열어 11단계가 다 채워진 걸 확인한다.

**변형 — 순서를 건너뛴다**: 인프라 아키텍처를 안 썼는데 API 명세부터 쓴다. 싱크독은 막지 않는다. 대시보드에 인프라가 `미작성`으로 남을 뿐이다.

**성공 조건**: 평소 작업 흐름을 바꾸지 않았는데 11단계 명세가 남아 있다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R5]], [[SYNC-PRD-001#R9]]

### S2 명세를 읽고 완료로 올린다

**주체**: 박호영
**상황**: 에이전트가 써놓은 PRD를 사람이 확인할 차례다.

1. 호영이 싱크독 웹에서 PRD를 연다. 사람용 뷰라 참조가 클릭 링크로 보이고, 클릭하면 RFQ의 해당 항목으로 간다.
2. 한 요구사항이 애매하다. 항목을 고르고 질문 탭에서 묻는다. 답을 보니 상위 RFQ에 근거가 없는 항목이었다.
3. Claude Code에서 "PRD R3 문단 이렇게 고쳐줘"라고 한다. 에이전트가 MCP로 수정한다. 새 버전이 생기고 커밋된다.
4. 다시 읽고 더 고칠 것이 없으면 상태를 `완료`로 바꾼다. 규약 오류·미완성·끊어진 참조가 있으면 올라가지 않는다.
5. 이후 MCP로 이 문서를 받는 에이전트는 상태가 `완료`인 걸 보고 확정 명세로 다룬다.

**변형 — 완료 후 수정**: 완료된 PRD를 나중에 고치면 자동으로 `초안`으로 내려간다. 에이전트가 다시 받으면 확정이 아님을 알게 된다.

**변형 — 동시 수정**: 호영이 에이전트 세션 둘을 돌리다 같은 문서를 거의 동시에 수정하려 한다. 늦은 쪽이 들고 있던 버전이 낡았으므로 쓰기가 거부되고 현재 버전과 내용이 돌아온다. 그 에이전트는 그걸 읽고 다시 판단한다.

**성공 조건**: 에이전트가 초안과 확정 명세를 구분한다. 두 세션이 같은 문서를 고쳐도 덮어쓰지 않는다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R6]], [[SYNC-PRD-001#R9]], [[SYNC-PRD-001#R11]]

### S3 코딩하면서 명세를 본다 (차순위)

**주체**: 박호영
**상황**: MINISPEC까지 다 나왔고 이제 구현한다.

1. 화면 한쪽에 싱크독을 띄운다. MINISPEC을 사람용 뷰로 열어두고 본다.
2. 다른 쪽 Claude Code에서 "MINISPEC 3번 구현해줘"라고 시킨다. 명세와 코드가 같은 저장소에 있으므로 에이전트는 clone된 파일로도, MCP로도 접근할 수 있다.
3. 에이전트가 해당 문서를 받는다. 상태가 `완료`인 걸 확인한다.
4. 본문에서 `[[SYNC-API-001#POST/orders]]` 참조를 발견하고 그 항목을 다시 요청해 읽는다. 필요하면 ERD 테이블 정의까지 따라간다.
5. 명세대로 코드가 나온다. 호영은 싱크독 화면의 명세와 결과를 대조한다.
6. 구현한 커밋 URL을 MINISPEC 항목에 코드 링크로 붙인다.

**변형 — 명세가 틀렸다**: 구현하다 보니 API 명세의 응답 필드가 ERD에 없다. 에이전트한테 시켜 API 명세를 고친다. 상태가 `초안`으로 내려간다. 이 항목을 참조하던 MINISPEC은 참조 패널에서 따라가 확인한다.

**성공 조건**: 에이전트가 구조를 임의로 정하지 않고 명세를 따른다.
**연관 요구사항**: [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R5]], [[SYNC-PRD-001#R6]], [[SYNC-PRD-001#R9]]

### S4 상위 명세가 바뀐다

**주체**: 박호영
**상황**: 요구사항 하나가 바뀌어 아래로 영향이 번진다.

1. 호영이 에이전트에게 PRD의 `#R12`를 고치게 한다. 에이전트가 MCP로 저장한다. PRD는 `초안`으로 내려간다.
2. 호영이 웹에서 R12를 고르고 참조 패널을 연다. 이 항목을 근거로 삼은 하위 항목 4개 — USECASE·API·ERD·MINISPEC — 가 보인다.
3. 하나씩 열어 본다. API와 MINISPEC은 고쳐야 한다. 에이전트에게 시킨다. 그 두 문서도 `초안`으로 내려간다. ERD는 영향이 없어 그대로 둔다.
4. 고친 문서를 다시 읽고 `완료`로 올린다.

**변형 — 오탈자**: 오타만 고쳤으면 2번부터는 안 한다. 아무것도 뜨지 않는다 — 하위를 둘러볼지는 사람이 정한다.

**변형 — 항목 삭제**: R12가 아예 빠지면 하위 항목 4개의 참조가 `끊어진 참조`로 표시된다. 프로젝트 상세의 수치와 그 문서들의 배너에 뜨고, 그 문서는 `완료`로 못 올라간다. 호영이 참조를 바꾸거나 항목을 같이 지운다. R12를 되살리면 표시가 저절로 풀린다.

**성공 조건**: 무엇이 무엇을 근거로 하는지 참조로 따라가고, 근거가 사라진 항목은 눈에 띈다.
**연관 요구사항**: [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R4]], [[SYNC-PRD-001#R8]]

### S5 다른 툴을 쓰는 사람이 자기 프로젝트를 굴린다 (차순위)

**주체**: 김민준
**상황**: 민준은 호영과 다른 에이전트 툴을 쓰고, 자기 프로젝트를 따로 가진다.

1. 민준이 자기 툴(Codex 또는 Gemini)에서 싱크독 MCP에 연결한다.
2. "이 저장소로 싱크독 시작해줘"라고 시킨다. 프로젝트가 등록되고 11단계 껍데기가 커밋된다. 웹 목록에는 자기 프로젝트만 보인다.
3. S1과 같은 흐름으로 명세를 쌓는다. 완료된 API 명세를 받아서 그걸 근거로 구현한다.
4. 구현하다 보니 명세에 빠진 게 보인다. 에이전트한테 시켜 MCP로 API 명세에 항목을 추가한다.
5. 추가된 내용은 사람이 쓴 것과 똑같이 새 버전이 되고, 참조가 추출된다. 작성 주체는 에이전트로 기록된다.
6. 문서 상태가 `초안`으로 내려간다. 민준이 웹에서 보고 완료 여부를 판단한다.

**성공 조건**: 툴이 달라도 같은 방식으로 명세를 읽고 쓴다. 누가·무엇으로 썼는지 추적된다.
**연관 요구사항**: [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R6]], [[SYNC-PRD-001#R9]]

---

### S6 명세를 사람 눈으로 훑어본다

**주체**: 박호영
**상황**: 설계 전체를 파악하거나 남에게 설명해야 한다.

1. 프로젝트 상세에서 "순서대로 읽기"를 연다. RFQ부터 MINISPEC까지 이어서 읽는다.
2. 시퀀스 다이어그램 단계에 오면 mermaid 코드가 아니라 그림으로 보인다. ERD도 마찬가지다.
3. 원본 탭으로 바꾸면 에이전트가 읽는 MD 그대로가 보인다. 필요하면 복사해 에이전트에게 붙여넣는다.
4. 참조 그래프를 열어 어느 요구사항이 어디까지 이어졌는지 본다. 참조가 하나도 없는 항목이 눈에 띈다.
5. 대시보드에서 `끊어진 참조`가 남아 있는 걸 발견하고 처리한다.

**성공 조건**: 사람이 설계 전체를 그림과 흐름으로 파악한다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R2]], [[SYNC-PRD-001#R8]], [[SYNC-PRD-001#R10]]

---

### S7 플랫폼 없이 명세에 접근한다

**주체**: 김민준
**상황**: 호영의 노트북이 꺼져 있어 싱크독 서버가 안 돈다.

1. 민준이 자기 프로젝트의 저장소를 clone한다. 명세가 `docs/specs/`에 코드와 함께 들어 있다.
2. 원본 MD를 그대로 읽는다. frontmatter에 상태가 있고, `[[]]` 참조로 어느 문서를 봐야 하는지 알 수 있다. 에이전트도 파일로 읽으면 된다.
3. 필요하면 로컬에서 MD를 고치고 push한다.
4. 나중에 싱크독 서버가 켜지면 그 커밋을 새 버전으로 인식하고, 참조 추출을 돌린다.

**성공 조건**: 플랫폼이 죽어도 명세가 잠기지 않는다.
**연관 요구사항**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R5]]
