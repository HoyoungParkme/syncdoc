# USECASE: 싱크독 (SyncDoc)

---

## 0. 이 문서의 형식

Cockburn 유스케이스 템플릿을 따른다. **26개 모두 같은 형식으로 쓴다.** 유스케이스마다 항목이 다르면 읽는 쪽이 매번 다시 적응해야 하고, 새 유스케이스를 추가할 때 어느 형식으로 쓸지 판단할 근거가 없어진다.

분량을 줄이는 일은 원본이 아니라 사람용 뷰가 맡는다. 원본을 줄이면 에이전트가 받을 정보까지 함께 줄어든다.

**항목**

| 항목 | 무엇을 적나 |
|---|---|
| 범위 | 어느 시스템을 기준으로 한 유스케이스인지 |
| 수준 | `사용자 목표` = 액터가 한 번에 이루려는 일 / `하위기능` = 다른 유스케이스에 딸려 실행되는 것 |
| 주 액터 | 목표를 가진 쪽 |
| 이해관계자와 관심사 | 결과에 이해가 걸린 쪽과 그들이 기대하는 것 |
| 사전조건 | 시작 전에 참이어야 하는 것 |
| 최소 보장 | 실패해도 지켜지는 것 |
| 성공 보장 | 성공했을 때 참이 되는 것 |
| 트리거 | 무엇이 이 흐름을 시작시키는가 |
| 패키지 | 이 유스케이스가 속한 기능 묶음. 다이어그램을 나누는 단위 |
| 포함(include) | 기본 흐름에서 **항상** 실행되는 다른 유스케이스 |
| 확장점(extension point) | 조건이 맞을 때만 다른 유스케이스가 끼어드는 지점. `조건` → 대상 |
| 일반화 | 이 유스케이스가 특수화한 상위 유스케이스 |
| 기본 흐름 | 번호 매긴 성공 경로 |
| 확장 | 기본 흐름에서 갈라지는 경우. `3a.`처럼 **몇 번 단계에서 갈라지는지**를 번호로 붙인다 |

별도의 "예외흐름" 절은 두지 않는다. 실패든 대안이든 모두 확장이며, 어느 단계에서 갈라지는지가 번호에 드러난다.

전체 26개. 사용자 목표 22개(추상 1 포함), 하위기능 4개.
**관계를 표에 선언하는 이유** — 다이어그램은 관계가 **있다**는 것을 보여주고, 명세서는 관계의 **조건과 시점**을 정의한다. 그림에서 `«include»` 화살표만 봐서는 그것이 기본 흐름 몇 번에서 불리는지 알 수 없다. 또한 관계가 표에 선언되어 있어야 다이어그램을 원본에서 생성할 수 있다. 흐름 문장을 사람이 읽고 판단해서 그리면, 명세를 고칠 때마다 그림이 어긋난다.

**두 개의 축** — 이 문서의 유스케이스 **목록**은 액터로 묶고, **다이어그램**은 패키지로 나눈다. 액터는 유스케이스를 *발견하는* 축이고, 패키지는 발견된 것을 *정리하는* 축이다. 액터로 다이어그램을 나누면 `UC-A6 → UC-S1~S5`처럼 액터 경계를 넘는 관계가 두 장에 걸쳐 끊긴다.

패키지는 사용자 행위 기준으로 짓는다. `문서 관리`·`참조 관리` 같은 명사형은 도메인 단계의 결론을 앞당겨 쓰는 것이므로 피한다.

| 패키지 | 유스케이스 | 수 |
|---|---|---|
| 명세 조회 | A2, A3, A4, A5, H2, H3, H4, H16, H19 | 9 |
| 명세 작성 | A1, A6, A7, A8, H7, H13, H17, H18, G1, S1, S2, S6, S7 | 13 |
| 검토·확정 | H6, H8, H14 | 3 |

협업 장치(전파·플래그·댓글·내 할 일)를 걷어내면서 `변경 추적` 패키지는 사라졌다([[SYNC-RFQ-001#Q6]]). 남은 것은 항목 삭제(H13)뿐이고, 그것은 명세 작성의 한 경우다.

**추상 유스케이스** — `UC-A0 명세를 조회한다`는 실제로 실행되지 않는다. UC-A2·A3·A5가 공통으로 가지는 "조회 대상을 지정하면 본문과 상태·버전이 돌아온다"를 묶은 것이며, 다이어그램에서 일반화 관계로만 나타난다.

- **나중의 자신** — 왜 이렇게 설계했는지 되짚을 수 있기를 바란다

#### UC-A1 프로젝트를 초기화한다

| 항목 | 내용 |
|---|---|
| 범위 | 싱크독 |
| 수준 | 사용자 목표 |
| 주 액터 | 에이전트 (또는 사람) |
| 이해관계자와 관심사 | **작업자**: 저장소 하나로 명세와 코드를 같이 관리하고 싶다.<br>**여러 프로젝트를 가진 사람**: 명세 위치와 구조가 프로젝트마다 같기를 바란다. |
| 사전조건 | 대상 GitHub 저장소가 존재하고, 싱크독이 그 저장소에 쓰기 권한을 가진다. |
| 최소 보장 | 실패해도 저장소가 훼손되지 않는다. 부분 생성된 디렉터리를 남기지 않는다. |
| 성공 보장 | 저장소가 싱크독 프로젝트로 등록되고, `docs/specs/` 아래 11단계 구조와 템플릿이 커밋된다. |
| 트리거 | 새 프로젝트를 시작하려고 초기화를 요청한다. |
| 패키지 | 명세 작성 |
| 포함(include) | — |
| 확장점(extension point) | `기존 명세 발견 시` → [[#UC-S6]] |
| 일반화 | — |

**기본 흐름**
1. 액터가 저장소 주소와 프로젝트 코드를 전달한다.
2. 시스템이 프로젝트 코드 형식(영문 대문자 4자 이내)과 중복을 검사한다.
3. 시스템이 저장소에 접근해 `docs/specs/`가 이미 있는지 확인한다. **커밋이 하나도 없는 빈 저장소도 받아들인다** — 4에서 만드는 커밋이 그 저장소의 첫 커밋이 된다. 새 프로젝트를 시작하는 가장 흔한 방법이 빈 저장소다.
4. 시스템이 11단계 + `STD` 디렉터리를 만들고, 싱크독이 관리하는 타입별 템플릿 12개를 `docs/specs/_templates/`에 복사해 한 번의 커밋으로 push한다.
5. 시스템이 프로젝트를 등록하고 11단계를 모두 `미작성`으로 초기화한다.
6. 시스템이 프로젝트 코드와 생성된 경로를 액터에게 알린다.

**확장**
- **2c. 같은 코드로 동시에 두 번 요청이 왔다**
  - 2c1. 시스템이 코드 단위 락으로 하나씩 처리한다. 뒤엣것은 2a(코드 중복)로 거부된다. 락이 없으면 서로의 작업 사본을 지운다.
- **2a. 프로젝트 코드가 중복이다**
  - 2a1. 시스템이 거부하고 이미 쓰이는 코드임을 알린다. 유스케이스 종료.
- **2b. 프로젝트 코드 형식이 틀렸다**
  - 2b1. 시스템이 규칙과 함께 거부한다. 유스케이스 종료.
- **2d. 이미 등록된 저장소다**
  - 2d1. 시스템이 거부하고 어느 프로젝트가 그 저장소를 쓰고 있는지 알린다. 유스케이스 종료. 한 저장소를 두 프로젝트가 나눠 쓰면 문서 ID가 겹쳐 서로의 이력을 덮어쓴다.
- **3a. `docs/specs/`가 이미 있다**
  - 3a1. 시스템이 덮어쓰지 않고, 기존 명세를 가져와 등록할지 액터에게 묻는다.
  - 3a2. 액터가 동의하면 시스템이 UC-S6(참조 인덱스 재구축)을 실행하고 등록한다.
  - 3a3. 액터가 거부하면 유스케이스 종료.
- **4a. 저장소 push가 실패한다**
  - 4a1. 시스템이 실패 원인(권한·네트워크)을 알리고 만들던 작업물을 버린다. 유스케이스 종료.

| 포함(include) | — |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 에이전트가 항목 ID로 참조 목록을 요청한다.
2. 시스템이 상위 참조(근거로 삼은 것)와 하위 참조(이 항목을 근거로 삼은 것)를 나눠 돌려준다.
3. 에이전트가 필요한 항목을 골라 UC-A3로 다시 요청한다.

**확장**
- **2a. 미존재 참조가 섞여 있다**
  - 2a1. 시스템이 해당 참조를 `미존재`로 표시해 함께 돌려준다.

  - 2b1. 시스템이 빈 목록을 돌려준다. 이는 고립 항목이라는 신호다.

**사후조건 참고**: 시스템이 참조를 미리 펼쳐 주지 않는다. 에이전트가 필요한 만큼만 따라간다.

#### UC-A6 명세를 작성·수정한다

| 항목 | 내용 |
|---|---|
| 범위 | 싱크독 |
| 수준 | 사용자 목표 |
| 주 액터 | 에이전트 |
| 이해관계자와 관심사 | **작업자**: 대화하며 결정한 내용이 손실 없이 남기를 바란다.<br>**같은 문서를 연 다른 세션**: 내가 보던 내용이 말없이 덮이지 않기를 바란다.<br>**나중에 읽을 사람**: 누가 무엇으로 썼는지 남기를 바란다. |
| 사전조건 | 프로젝트가 등록되어 있다. 수정일 경우 액터가 UC-A2로 받은 버전을 보유한다. |
| 최소 보장 | 규약을 위반한 내용은 저장되지 않는다. 저장에 실패해도 기존 버전이 손상되지 않는다. |
| 성공 보장 | 새 버전이 생기고 저장소에 커밋된다. 참조가 추출된다. 작성 주체가 기록된다. |
| 트리거 | 대화에서 결정된 내용을 명세로 남기려 한다. |
| 패키지 | 명세 작성 |
| 포함(include) | [[#UC-S1]], [[#UC-S2]], [[#UC-S7]] |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 에이전트가 문서 타입·본문·커밋 메시지(요약과 이유)와 함께 생성 또는 수정을 요청한다. 수정이면 보유한 버전을 함께 보낸다. 항목 ID는 에이전트가 본문에 직접 붙인 것이다.
2. 시스템이 UC-S1(규약 검증)을 실행한다.
3. 생성이면 시스템이 문서 ID를 발급하고 문서 타입 템플릿을 적용한다. DOM이면 선행조건([[SYNC-STD-001]] 2.6)을 본다.
4. 수정이면 시스템이 보낸 버전과 현재 버전이 같은지 확인한다.
5. 시스템이 본문을 저장하고 UC-S7(저장소 커밋)로 커밋한다.
6. 시스템이 UC-S2를 실행한다.
7. 시스템이 작성 주체를 에이전트로, 지시한 사람 계정과 함께 기록한다.
8. 시스템이 새 버전 번호와 처리 결과를 액터에게 돌려준다. 결과에는 **다음 할 일**이 담긴다 — 사람에게 웹에서 읽으라고 하고 멈추라는 것([[SYNC-STD-001]] 1.8).

**확장**
- **2a. 규약을 위반했다**
  - 2a1. 시스템이 어느 부분이 어떻게 틀렸는지 돌려주고 저장하지 않는다. 유스케이스 종료.
- **3a. DOM 선행조건이 안 맞는다**
  - 3a1. 시스템이 무엇이 먼저 있어야 하는지(API 문서 또는 클래스 명세)와 지금 있는 DOM 문서 목록을 돌려주고 저장하지 않는다. 유스케이스 종료.
- **4a. 보낸 버전이 현재 버전과 다르다**
  - 4a1. 시스템이 쓰기를 거부하고 현재 버전과 본문을 돌려준다.
  - 4a2. 에이전트가 상대 변경을 반영해 1번부터 다시 시도하거나, 사람에게 판단을 넘긴다.
- **4b. 본문에서 항목 ID가 사라졌다 (항목 삭제)**
  - 4b1. 시스템이 사라진 항목과 그것을 참조하는 하위 항목 목록을 돌려주고 저장하지 않는다.
  - 4b2. 에이전트가 지시한 사람에게 보여주고 확인을 받는다.
  - 4b3. 확인되면 에이전트가 삭제 확인 표시와 함께 다시 요청한다. 시스템이 저장하고 항목 ID를 `삭제됨`으로 남기며, 그것을 가리키던 참조를 `끊어진 참조`로 표시한다(UC-S2 2c).
  - 4b4. 하위 참조가 없으면 이 확장은 일어나지 않는다.
- **5a. 커밋 push가 실패한다**
  - 5a1. 시스템이 pull 후 재시도한다.
  - 5a2. 재시도도 실패하면 저장을 되돌리고 액터에게 알린다. 유스케이스 종료.
- **6a. 대상 문서가 `완료` 상태였다**
  - 6a1. 시스템이 상태를 `초안`으로 내리고 이력에 남긴다.
  - 6a2. 내린 상태는 **저장소 원본에도 반영된다.** 에이전트·되돌리기가 부른 저장은 그 저장의 커밋에 함께 담기고, GitHub push가 부른 저장은 상태 커밋이 하나 더 생긴다.

**연관**: [[SYNC-PRD-001#R1]], [[SYNC-PRD-001#R3]], [[SYNC-PRD-001#R9]] / [[SYNC-SCN-001#S1]], [[SYNC-SCN-001#S2]], [[SYNC-SCN-001#S3]], [[SYNC-SCN-001#S5]]

3. 시스템이 커밋 이력에서 버전 목록을 다시 만든다.

**확장**
- **2a. 규약을 위반한 파일이 있다**
  - 2a1. 시스템이 `규약 오류`로 표시하고 나머지 파일 처리를 계속한다.

**사후조건 참고**: DB 없이 저장소만으로 참조 관계가 복원된다는 것을 보장한다.
