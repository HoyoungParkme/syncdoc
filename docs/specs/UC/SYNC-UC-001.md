# USECASE: 싱크독 (SyncDoc)

---

## 0. 이 문서의 형식

Cockburn 유스케이스 템플릿을 따른다. **30개 모두 같은 형식으로 쓴다.** 유스케이스마다 항목이 다르면 읽는 쪽이 매번 다시 적응해야 하고, 새 유스케이스를 추가할 때 어느 형식으로 쓸지 판단할 근거가 없어진다.

분량을 줄이는 일은 원본이 아니라 사람용 뷰가 맡는다. 원본을 줄이면 에이전트가 받을 정보까지 함께 줄어든다.

**항목**

| 항목 | 무엇을 적나 |
|---|---|
| 범위 | 어느 시스템을 기준으로 한 유스케이스인지 |
| 수준 | `사용자 목표` = 액터가 한 번에 이루려는 일 / `하위기능` = 다른 유스케이스에 딸려 실행되는 것 |
| 주 액터 | 목표를 가진 쪽 |
| 이해관계자와 관심사 | 결과에 이해가 걸린 쪽과 그들이 기대하는 것 |
| 사전조건 | 시작 전에 참이어야 하는 것 |
| 최소 보장 | 실패해도 지켜지는 것 |
| 성공 보장 | 성공했을 때 참이 되는 것 |
| 트리거 | 무엇이 이 흐름을 시작시키는가 |
| 패키지 | 이 유스케이스가 속한 기능 묶음. 다이어그램을 나누는 단위 |
| 포함(include) | 기본 흐름에서 **항상** 실행되는 다른 유스케이스 |
| 확장점(extension point) | 조건이 맞을 때만 다른 유스케이스가 끼어드는 지점. `조건` → 대상 |
| 일반화 | 이 유스케이스가 특수화한 상위 유스케이스 |
| 기본 흐름 | 번호 매긴 성공 경로 |
| 확장 | 기본 흐름에서 갈라지는 경우. `3a.`처럼 **몇 번 단계에서 갈라지는지**를 번호로 붙인다 |

별도의 "예외흐름" 절은 두지 않는다. 실패든 대안이든 모두 확장이며, 어느 단계에서 갈라지는지가 번호에 드러난다.

전체 28개. 사용자 목표 22개(추상 1 포함), 하위기능 6개.
**관계를 표에 선언하는 이유** — 다이어그램은 관계가 **있다**는 것을 보여주고, 명세서는 관계의 **조건과 시점**을 정의한다. 그림에서 `«include»` 화살표만 봐서는 그것이 기본 흐름 몇 번에서 불리는지 알 수 없다. 또한 관계가 표에 선언되어 있어야 다이어그램을 원본에서 생성할 수 있다. 흐름 문장을 사람이 읽고 판단해서 그리면, 명세를 고칠 때마다 그림이 어긋난다.

**두 개의 축** — 이 문서의 유스케이스 **목록**은 액터로 묶고, **다이어그램**은 패키지로 나눈다. 액터는 유스케이스를 *발견하는* 축이고, 패키지는 발견된 것을 *정리하는* 축이다. 액터로 다이어그램을 나누면 `UC-A6 → UC-S1~S5`처럼 액터 경계를 넘는 관계가 두 장에 걸쳐 끊긴다.

패키지는 사용자 행위 기준으로 짓는다. `문서 관리`·`참조 관리` 같은 명사형은 도메인 단계의 결론을 앞당겨 쓰는 것이므로 피한다.

| 패키지 | 유스케이스 | 수 |
|---|---|---|
| 명세 조회 | A2, A3, A4, A5, H2, H3, H4, H16 | 8 |
| 명세 작성 | A1, A6, H7, G1, S1, S2, S6, S7 | 8 |
| 변경 추적 | H10, H11, H12, H13, S3, S4 | 6 |
| 검토·확정 | H6, H8, H9, H14, H15 | 5 |

**추상 유스케이스** — `UC-A0 명세를 조회한다`는 실제로 실행되지 않는다. UC-A2·A3·A5가 공통으로 가지는 "조회 대상을 지정하면 본문과 상태·버전이 돌아온다"를 묶은 것이며, 다이어그램에서 일반화 관계로만 나타난다.

## 1. 액터

| 액터 | 코드 | 설명 | 접근 경로 |
|---|---|---|---|
| 사람 | H | 박호영, 김민준. 명세를 읽고 확정하고 검토한다 | 웹 |
| 에이전트 | A | Claude Code, Codex, Gemini 등. 사람의 지시로 명세를 읽고 쓴다 | MCP |
| GitHub | G | 명세 원본이 사는 코드 저장소. 밖에서 일어난 변경을 알려온다 | webhook |

**시스템 경계**: 싱크독 서버(웹 + MCP 서버 + DB)가 안쪽이다. 에이전트 툴, 브라우저, GitHub는 바깥이다.

**공통 이해관계자** — 개별 유스케이스에 반복해 적지 않고 여기 한 번만 둔다.
- **명세를 읽고 구현하는 팀원** — 낡은 명세를 보고 개발하지 않기를 바란다
- **나중에 합류할 사람** — 왜 이렇게 설계했는지 되짚을 수 있기를 바란다

#### UC-A1 프로젝트를 초기화한다

| 항목 | 내용 |
|---|---|
| 범위 | 싱크독 |
| 수준 | 사용자 목표 |
| 주 액터 | 에이전트 (또는 사람) |
| 이해관계자와 관심사 | **작업자**: 저장소 하나로 명세와 코드를 같이 관리하고 싶다.<br>**팀원**: 명세 위치와 구조가 프로젝트마다 같기를 바란다. |
| 사전조건 | 대상 GitHub 저장소가 존재하고, 싱크독이 그 저장소에 쓰기 권한을 가진다. |
| 최소 보장 | 실패해도 저장소가 훼손되지 않는다. 부분 생성된 디렉터리를 남기지 않는다. |
| 성공 보장 | 저장소가 싱크독 프로젝트로 등록되고, `docs/specs/` 아래 11단계 구조와 템플릿이 커밋된다. |
| 트리거 | 새 프로젝트를 시작하려고 초기화를 요청한다. |
| 패키지 | 명세 작성 |
| 포함(include) | — |
| 확장점(extension point) | `기존 명세 발견 시` → [[#UC-S6]] |
| 일반화 | — |

**기본 흐름**
1. 액터가 저장소 주소와 프로젝트 코드를 전달한다.
2. 시스템이 프로젝트 코드 형식(영문 대문자 4자 이내)과 중복을 검사한다.
3. 시스템이 저장소에 접근해 `docs/specs/`가 이미 있는지 확인한다.
4. 시스템이 11단계 + `STD` 디렉터리를 만들고, 싱크독이 관리하는 타입별 템플릿 12개를 `docs/specs/_templates/`에 복사해 한 번의 커밋으로 push한다.
5. 시스템이 프로젝트를 등록하고 11단계를 모두 `미작성`으로 초기화한다.
6. 시스템이 프로젝트 코드와 생성된 경로를 액터에게 알린다.

**확장**
- **2c. 같은 코드로 동시에 두 번 요청이 왔다**
  - 2c1. 시스템이 코드 단위 락으로 하나씩 처리한다. 뒤엣것은 2a(코드 중복)로 거부된다. 락이 없으면 서로의 작업 사본을 지운다.
- **2a. 프로젝트 코드가 중복이다**
  - 2a1. 시스템이 거부하고 이미 쓰이는 코드임을 알린다. 유스케이스 종료.
- **2b. 프로젝트 코드 형식이 틀렸다**
  - 2b1. 시스템이 규칙과 함께 거부한다. 유스케이스 종료.
- **3a. `docs/specs/`가 이미 있다**
  - 3a1. 시스템이 덮어쓰지 않고, 기존 명세를 가져와 등록할지 액터에게 묻는다.
  - 3a2. 액터가 동의하면 시스템이 UC-S6(참조 인덱스 재구축)을 실행하고 등록한다.
  - 3a3. 액터가 거부하면 유스케이스 종료.
- **4a. 저장소 push가 실패한다**
  - 4a1. 시스템이 실패 원인(권한·네트워크)을 알리고 만들던 작업물을 버린다. 유스케이스 종료.

#### UC-A6 명세를 작성·수정한다

| 항목 | 내용 |
|---|---|
| 범위 | 싱크독 |
| 수준 | 사용자 목표 |

| 성공 보장 | 새 버전이 생기고 저장소에 커밋된다. 참조가 추출되고 변경 영향이 판정된다. 작성 주체가 기록된다. |

| 포함(include) | [[#UC-S1]], [[#UC-S2]], [[#UC-S3]], [[#UC-S7]] |
| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 에이전트가 문서 타입·본문·커밋 메시지(요약과 이유)와 함께 생성 또는 수정을 요청한다. 수정이면 보유한 버전과 **이번에 바꾼 항목 ID 목록**을 함께 보낸다. 항목 ID는 에이전트가 본문에 직접 붙인 것이다. 이 변경으로 **상위 항목과 어긋나게 됐음을 알면** 그 상위 항목 ID 목록도 함께 보낸다.
2. 시스템이 UC-S1(규약 검증)을 실행한다.
3. 생성이면 시스템이 문서 ID를 발급하고 문서 타입 템플릿을 적용한다.
4. 수정이면 시스템이 보낸 버전과 현재 버전이 같은지 확인한다.
5. 시스템이 본문을 저장하고 UC-S7(저장소 커밋)로 커밋한다.
6. 시스템이 UC-S2, UC-S3을 순서대로 실행한다. 어긋난 상위 항목이 지정됐으면 그 항목에 `하위 불일치` 플래그를 붙인다([[#UC-S4]]). 담당자는 상위 문서 최근 작성자.
7. 시스템이 작성 주체를 에이전트로, 지시한 사람 계정과 함께 기록한다.
8. 시스템이 새 버전 번호와 처리 결과를 액터에게 돌려준다.

**확장**
- **2a. 규약을 위반했다**
  - 2a1. 시스템이 어느 부분이 어떻게 틀렸는지 돌려주고 저장하지 않는다. 유스케이스 종료.
- **4a. 보낸 버전이 현재 버전과 다르다**
  - 4a1. 시스템이 쓰기를 거부하고 현재 버전과 본문을 돌려준다.
  - 4a2. 에이전트가 상대 변경을 반영해 1번부터 다시 시도하거나, 사람에게 판단을 넘긴다.
- **4b. 본문에서 항목 ID가 사라졌다 (항목 삭제)**
  - 4b1. 시스템이 사라진 항목과 그것을 참조하는 하위 항목 목록을 돌려주고 저장하지 않는다.
  - 4b2. 에이전트가 지시한 사람에게 보여주고 확인을 받는다.
  - 4b3. 확인되면 에이전트가 삭제 확인 표시와 함께 다시 요청한다. 시스템이 저장하고 항목 ID를 `삭제됨`으로 남기며 하위에 `끊어진 참조` 플래그를 붙인다.
  - 4b4. 하위 참조가 없으면 이 확장은 일어나지 않는다.
- **5a. 커밋 push가 실패한다**
  - 5a1. 시스템이 pull 후 재시도한다.
  - 5a2. 재시도도 실패하면 저장을 되돌리고 액터에게 알린다. 유스케이스 종료.
- **6a. 대상 문서가 `승인` 상태였다**
  - 6a1. 시스템이 상태를 `검토중`으로 내리고 이력에 남긴다.

**기본 흐름**

2. 시스템이 미해결 댓글이 있으면 개수를 보여준다.
3. `승인`으로 가면 시스템이 **이 문서가 참조하는 상위 항목 목록**(문서·항목·현재 버전)을 보여준다. 사람이 하나씩 보고 이 문서와 어긋난 것에 표시한다. 표시가 없어도 "어긋난 곳 없음"을 확인해야 진행된다.

- **1a. 문서에 규약 오류 또는 미완성 경고가 있고 `승인`으로 가려 한다**
  - 1a1. 시스템이 전환을 막고 오류·경고 목록을 알린다. 유스케이스 종료. `검토중`으로 가는 것은 막지 않는다.
- **2a. 미해결 댓글이 있는데 `승인`으로 올리려 한다**

- **3a. 상위 항목이 어긋났는데 이 문서가 아니라 상위를 고쳐야 한다**
  - 3a1. 사람이 그 상위 항목을 표시하고 승인을 진행한다. 상위 담당자가 `하위 불일치` 플래그를 보고 처리한다([[#UC-H11]]).
- **3b. 이 문서 자체를 고쳐야 한다**
  - 3b1. 승인하지 않고 닫는다. 에이전트에게 고치게 한 뒤 다시 시도한다.
- **3c. 상위 문서가 아직 `승인`이 아니다**
  - 3c1. 시스템이 목록에 그 사실을 표시하고 전환을 진행한다. 상태는 게이트가 아니라 신호다.

**사후조건 참고**: 권한 제한이 없으므로 누구나 이 유스케이스를 수행한다. 승인 여부는 대화로 합의한 뒤 누른다.

**확장**

- **3a. 프로젝트에 문서가 하나도 없다**
  - 3a1. 시스템이 11단계를 모두 `미작성`으로 보여준다.

| 항목 | 내용 |

| 확장점(extension point) | — |
| 일반화 | — |

**기본 흐름**
1. 시스템이 MD 파일을 `docs/specs/` 경로에 쓴다.
2. 시스템이 규격화된 메시지로 커밋하고 push한다. 본문 변경은 `spec(문서ID): 요약`, 상태 변경만이면 `status(문서ID): 이전 → 새상태` 형식이다. 작성 주체는 커밋 작성자로 남긴다.

**확장**

  - 2a1. 시스템이 pull 후 재시도한다.
- **2b. 재시도도 실패한다**
  - 2b1. 시스템이 저장을 되돌리고 액터에게 알린다. 유스케이스 종료.
- **2c. 첨부 파일이 함께 저장된다**
  - 2c1. 시스템이 `docs/specs/assets/` 경로에 함께 담아 한 커밋으로 만든다.
