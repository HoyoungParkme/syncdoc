# PRD: 싱크독 (SyncDoc)

---

## 1. 목표

#### G1 평소 쓰는 에이전트와 대화하다가 결정된 내용이 그대로 명세로 남는다

#### G2 11단계 명세 체인을 한 곳에서 조회하고 확정한다

#### G3 명세끼리 항목 단위로 연결되어 근거를 역추적할 수 있다

#### G4 상위 명세가 바뀌면 영향받는 하위 명세가 자동으로 식별된다

#### G5 각자 쓰는 에이전트가 툴에 상관없이 명세를 읽고 쓸 수 있다

#### G6 명세 원본은 에이전트가 읽기 좋게 쓰고, 사람은 거기서 파생된 뷰로 본다

#### G7 한 사람이 여러 프로젝트를 쓰고, 여러 사람이 각자 자기 프로젝트를 쓴다


## 2. 비목표

| 비목표 | 이유 |
|---|---|
| 플랫폼이 명세를 **쓰는** AI — 초안 생성·본문 자동 수정 | 쓰기는 각자의 에이전트가 MCP로 한다. 본문을 쓰는 경로는 MCP와 저장소 push(GitHub 또는 서버 저장소) 둘뿐이다([[#R9]]) |
| 플랫폼이 명세를 **판정하는** AI — 정합성 검사·완료 판단 | 완료는 사람이 누른다([[#R6]]). 모델 판단이 이력에 남으면 안 된다 |
| 웹 원본 편집기 | 명세 본문은 각자의 에이전트가 MCP로 쓴다. 사람이 웹에서 직접 고치면 에이전트가 관리하는 흐름과 어긋나고, 검사·충돌·삭제 확인을 사람이 손으로 하게 된다 |
| 사람용 뷰 직접 편집 | MD 원본이 유일한 원본. 뷰 편집을 허용하면 원본이 둘이 되어 반드시 어긋남 |
| 코드 저장소 대체 | GitHub 프로젝트의 코드는 GitHub에 두고 링크만 연결한다. 서버 저장소([[#R14]])는 git 원격 하나다 — 코드 브라우저·PR·이슈 화면은 없다 |
| 단계 순서 강제 | RFQ에서 "권장이지 강제 아님"으로 확정 |
| 역할·권한 관리 | 역할이 없다. 프로젝트 안에서 할 수 있는 일은 하나뿐이다 — 소유자는 다 하고, 아닌 사람은 못 본다. 읽기 전용·검토자·관리자 같은 층을 두지 않는다 |
| 이슈 트래커·일정 관리 | 별도 도구 영역 |
| 기존 문서 이관 | 앞으로의 문서만 싱크독에서 쓴다 |
| macOS판 | 요청자의 환경이 윈도·리눅스다. 싱크독_로컬 설치 파일은 둘만 만든다 |
| 자동 업데이트 | 폐쇄망에서는 내려받을 곳이 없다. 새 판은 설치 파일로 들여와 덮어 설치한다 |
| 코드 서명 | 개인이 받을 길이 없다. 설치 때 「알 수 없는 게시자」 경고를 받아들인다 |

**「전달」의 경계.** 위 두 줄이 막는 것은 **쓰기와 판정**이다. **읽는 사람에게 전달하는 것**은 여기 들지 않는다 — 모델이 같은 프로젝트를 읽게 하여 묻고 답을 받는 것은 쓰기도 판정도 아니다([[#R11]]). 경계는 하나다 — 명세를 **바꾸지 않는다**(쓰기 경로는 R9 그대로). 대화와 첨부는 **읽는 사람의 메모**로 보관하되 명세 표와 분리된 표에 산다 — 쓰기도 판정도 아니고, 저장소에는 아무것도 남지 않는다. 남길 값이 있으면 사람이 자기 에이전트에게 말해 명세에 넣는다 — 그것도 R9의 쓰기 경로다. (전에는 「답도 저장하지 않는다」가 둘째 경계였다. 2026-09-29 사용자 결정으로 대화·첨부를 보관한다 — 후속 질문, 다른 기기에서 이어 가기, 캡처를 붙여 묻기에 브라우저만으로는 모자랐다. 경계가 하나로 좁아졌을 뿐 「쓰기와 판정을 막는다」는 그대로다)

**「소유」의 경계.** 「역할·권한 관리」 줄이 막는 것은 **역할**이다. 한 프로젝트 안에서 사람마다 할 수 있는 일이 다른 상태를 만들지 않는다. **누구 것인가**는 그와 다른 문제이고, 목표다([[#R12]]) — 프로젝트를 등록한 사람만 그 프로젝트를 보고 쓴다. 경계는 둘로 지킨다. 소유자는 **한 명**이고(옮기지도 나누지도 않는다), 소유자가 아니면 **아예 없는 것처럼 보인다**(목록에도 안 뜨고 주소를 직접 쳐도 없다고 답한다). 초대·공유·멤버는 없다.

## 3. 요구사항

11개 기능 전부 v1 범위다. 우선순위 구분은 두지 않되, R1·R5는 나머지가 올라서는 바닥이므로 먼저 구현한다.

### 3.1 기능 요구사항

#### R1 에이전트용 원본과 사람용 뷰

근거: [[SYNC-RFQ-001#Q1]]

명세는 에이전트가 읽을 것을 전제로, 규약이 있는 Markdown으로 작성한다. 이 MD가 원본이자 에이전트용 산출물이다. 항목 ID·`[[]]` 참조 문법·다이어그램 코드블록·frontmatter는 모두 에이전트가 파싱하기 위한 규약이다.

사람용 뷰는 원본에 그림·참조 링크·상태 표시를 더해 파생 생성한다. 마크다운을 HTML로 변환하는 것이 아니라, 사람이 보는 데 필요한 정보를 얹은 별도 표현이다.

- [ ] 원본 규약은 [[SYNC-STD-001]] 명세 작성 규약을 따른다. **규약 위반**(파싱 불가)은 저장을 거부하고, **미완성**(필수 절 누락)은 저장하되 경고한다
- [ ] 에이전트가 원본 MD를 그대로 읽어도 문서 구조·참조·상태를 파악할 수 있다
- [ ] 사람용 뷰에서 다이어그램은 그림으로, `[[]]`는 클릭 링크로, 상태는 뱃지로 표시된다
- [ ] 웹 문서 뷰는 **유저용**(사람용 뷰, 기본)과 **원본**(에이전트가 읽는 MD 그대로) 두 탭을 전환해 보여준다. 원본 탭은 읽기와 복사만 된다
- [ ] 사람용 뷰에 목차와 단계 간 이동이 있다
- [ ] 사람용 뷰 자체는 편집 대상이 아니며, 원본이 바뀌면 갱신된다
- [x] 11단계 문서 타입별 원본 템플릿을 싱크독이 관리한다. **저장소에 사본을 두지 않는다** — 초기화가 만드는 README가 싱크독 저장소를 링크로 가리키고, MCP는 앱에 내장된 원본을 준다(카드 AB, #113·#129). 사본을 복사하던 v1은 규약이 바뀌어도 갱신되지 않아 여덟 저장소가 낡은 안내를 들고 있었다
- [ ] 템플릿은 MCP 도구의 문서 생성에 적용된다

#### R2 ID 기반 상호참조

근거: [[SYNC-RFQ-001#Q3]]

문서와 문서 내 항목에 ID를 부여한다. 본문에서 `[[ID]]`로 참조하면 저장 시 참조 관계가 추출되어 기록된다. 항목 클릭 시 상위 참조(근거)와 하위 참조(파생)를 모두 보여준다. ID 규칙은 5장.

- [ ] 저장 시 본문의 참조가 자동 추출되어 참조 테이블에 반영된다
- [ ] 존재하지 않는 ID를 참조하면 저장은 되되 해당 줄에 경고가 표시된다
- [ ] 항목 상세에서 상·하위 참조가 문서 타입별로 구분되어 보인다
- [ ] 항목 ID는 **작성자(사람 또는 에이전트)가 본문에 직접 붙인다.** 시스템은 발급하지 않고 형식·문서 내 유일성·삭제된 ID 재사용 여부만 검증한다
- [ ] 항목 ID는 발급 후 재사용되지 않는다 (삭제해도 회수 안 함)
- [ ] `[[` 입력 시 같은 프로젝트의 ID가 자동완성된다
- [ ] 프로젝트 전체의 참조 그래프를 조회할 수 있다
- [ ] 참조를 누르면 그 항목 블록만 그 자리에서(팝업) 본다 — 보던 화면을 떠나지 않는다. 문서로 가기·새 창은 선택이다(카드 BH)

#### R3 버전 관리

근거: [[SYNC-RFQ-001#Q3]]

저장할 때마다 새 버전이 생긴다. 덮어쓰기 없음. 버전 = GitHub 커밋. 두 버전 간 diff를 줄 단위로 보여준다.

- [ ] 저장 10번이면 버전 10개가 조회된다
- [ ] 버전 두 개를 골라 diff를 볼 수 있다
- [ ] 버전마다 작성 주체(사람 / 에이전트)와 계정이 기록된다
- [ ] 되돌리기는 "이전 내용으로 새 버전 생성"이며 이력이 지워지지 않는다

#### R4 변경 추적

근거: [[SYNC-RFQ-001#Q3]] · [[SYNC-RFQ-001#Q6]]

추적하는 것은 하나 — **끊어진 참조**다. 상위 항목이 삭제되면(항목 삭제·문서 휴지통·파일 삭제) 그것을 가리키던 하위 참조가 `끊어진 참조`로 표시된다. 상위가 돌아오면 저절로 풀린다. 담당자·확인 처리·전파 결정·이력은 두지 않는다 — 혼자 쓰는 도구에서 통보받을 상대는 자기 자신이고, 무엇을 고칠지는 참조를 따라가 읽으면 된다([[#R2]]).

상위 항목이 **수정**됐을 때는 아무것도 붙지 않는다. 고친 사람이 곧 하위를 쓴 사람이다. 하위를 둘러볼지는 참조 패널을 보고 스스로 정한다.

- [ ] 상위 항목 삭제 시 이를 참조하는 하위 항목의 참조가 `끊어진 참조`로 표시된다. 하위 문서를 다시 저장하지 않아도 표시된다
- [ ] 항목 삭제 시 하위 참조 목록을 보여주고 확인받은 뒤에 저장한다
- [ ] `끊어진 참조`는 문서 뷰 배너·참조 패널·프로젝트 상세 수치 세 곳에서 보인다
- [ ] 상위가 되살아나거나 다시 쓰이면 표시가 저절로 풀린다
- [ ] `끊어진 참조`가 있는 문서는 `완료`로 올릴 수 없다([[#R6]])

#### R5 스토리지 (저장소 연동)

근거: [[SYNC-RFQ-001#Q3]]

명세 원본(MD)은 **각 프로젝트의 코드 저장소 안 `docs/specs/`** 에 둔다. 명세와 코드가 같은 저장소에서 같이 버전 관리되므로, 특정 커밋 시점의 명세를 그대로 되짚을 수 있다. 참조 관계·버전 같은 메타데이터는 노트북 서버의 DB에 두되, 전부 저장소에서 재구축된다([[#N3]]).

- [ ] 저장소를 등록하면 `docs/specs/` 아래 명세를 인식한다
- [ ] 저장소를 여러 개 등록할 수 있다 (프로젝트 = 저장소 1개)
- [ ] 저장소는 프로젝트마다 GitHub 저장소 또는 서버 저장소다([[#R14]])
- [ ] 프로젝트 초기화 시 `docs/specs/` 디렉터리 구조와 11단계 템플릿 껍데기가 커밋된다
- [ ] 프로젝트 초기화는 MCP 도구와 웹 양쪽에서 실행할 수 있다
- [ ] 플랫폼에서 저장하면 해당 저장소에 커밋된다
- [ ] 저장소(GitHub 또는 서버 저장소)에 직접 push된 변경이 플랫폼에 반영된다
- [ ] DB가 유실되어도 저장소만으로 참조 관계를 재구축할 수 있다
- [x] 첨부 파일은 `docs/specs/assets/` 경로에 두고 MD에서 상대 경로로 참조한다 — 앱이 `GET /api/projects/{code}/files/{path}`로 작업 사본의 파일을 준다. 화면 배치 html의 이미지·폰트가 이 길로 뜬다(카드 Z)

#### R6 단계별 상태

근거: [[SYNC-RFQ-001#Q3]] · [[SYNC-RFQ-001#Q6]]

문서 상태는 `초안` / `완료` 둘. 상태는 게이트가 아니라 신호다. 확정 여부를 사람과 에이전트에게 알려줄 뿐, 하위 단계 작성을 막지 않는다. 완료는 쓰게 시킨 사람이 읽어 보고 스스로 누른다. 검토중·승인·상위 대조는 두지 않는다 — 검토할 상대가 없다.

**예외 하나 — DOM 안의 선행조건.** 클래스 명세는 API 문서가, ERD는 클래스 명세가 같은 프로젝트에 **있어야** 만들 수 있다([[SYNC-STD-001]] 2.6). 판정은 존재이지 상태가 아니다 — 게이트가 아니라는 원칙은 그대로다. 셋을 예측으로 한 번에 채우는 것만 막는다.

- [ ] 문서 상태를 웹에서 `초안`⇄`완료`로 바꿀 수 있다. 에이전트(MCP)도 같은 조건으로 바꿀 수 있다 — 사람이 시켰을 때, 또는 에이전트가 다 썼다고 판단했을 때(카드 BE). 완료로 올리는 조건은 입구와 무관하게 같다
- [ ] 상태 변경 이력(누가·언제·무엇→무엇)이 남는다. 에이전트가 바꿨으면 에이전트와 지시한 사람으로 남는다
- [ ] 상위 문서가 초안이어도 하위 문서 작성·완료가 가능하다
- [ ] DOM 클래스 명세·ERD는 선행 문서(API 문서·클래스 명세)가 없으면 만들 수 없다 — 존재 판정
- [ ] 완료 문서가 수정되면 `초안`으로 내려간다. 원본 frontmatter에도 반영된다
- [ ] 규약 오류·미완성 경고·끊어진 참조가 있는 문서는 `완료`로 바꿀 수 없다. `초안`으로 내리는 것은 막지 않는다

#### R8 프로젝트 대시보드

근거: [[SYNC-RFQ-001#Q3]]

프로젝트별로 11단계 진행 상태를 한 화면에서 본다.

- [ ] 프로젝트 목록에서 11단계 상태가 색으로 표시된다
- [ ] 프로젝트 상세에서 단계별 문서·끊어진 참조 수·규약 오류·미완성 수·최근 변경이 보인다
- [ ] 끊어진 참조나 규약 오류가 있는 프로젝트는 목록에서 눈에 띈다
- [ ] 수치 클릭 시 해당 항목 목록으로 이동한다
- [ ] 11단계를 순서대로 이어서 읽는 모드가 있다

#### R9 MCP 서버

근거: [[SYNC-RFQ-001#Q2]]

에이전트가 툴에 상관없이 붙을 수 있도록 MCP 서버를 제공한다. **명세 본문을 쓰는 경로는 MCP와 저장소 직접 push(GitHub 또는 서버 저장소) 둘뿐이다.** 사람은 자기 에이전트와 대화하다가 결정된 내용을 에이전트가 싱크독에 반영한다. 웹은 읽기·상태 변경·되돌리기·휴지통까지만 한다.

- [ ] 특정 문서·항목을 조회하는 도구를 제공한다
- [ ] 문서·항목 조회 결과에 상태(초안/완료)와 버전이 함께 담긴다. 에이전트가 확정 명세와 초안을 구분할 수 있다
- [ ] 항목의 상위·하위 참조 목록을 조회하는 도구를 제공한다. 에이전트가 참조를 따라 필요한 것만 다시 요청할 수 있다
- [ ] 프로젝트의 문서 목록과 각 문서의 상태를 조회하는 도구를 제공한다
- [ ] 문서를 생성·수정하는 도구를 제공한다. 생성 시 문서 타입 템플릿이 적용된다
- [ ] 프로젝트를 초기화하는 도구를 제공한다
- [ ] 수정 도구는 조회 시 받은 버전을 함께 보내야 한다. 그 사이 문서가 바뀌었으면 쓰기를 거부하고 현재 버전과 내용을 돌려준다
- [ ] MCP로 쓴 내용도 사람이 쓴 것과 동일하게 버전 생성·참조 추출을 거친다
- [ ] MCP 작성분은 작성 주체가 에이전트로 기록된다
- [ ] Claude Code, Codex, Gemini 등 서로 다른 클라이언트에서 동작한다
- [ ] 저장소(GitHub 또는 서버 저장소)를 clone해 파일로 직접 읽는 것도 가능하다

#### R10 다이어그램 렌더링

근거: [[SYNC-RFQ-001#Q1]]

원본의 다이어그램 코드블록(mermaid)을 사람용 뷰에서 그림으로 렌더링한다. 렌더링은 브라우저가 하며 서버는 생성물을 만들지 않는다. 에이전트는 원본의 텍스트를 그대로 읽으므로 그림을 필요로 하지 않는다.

- [ ] mermaid 코드블록이 사람용 뷰에서 다이어그램으로 렌더링된다
- [ ] 원본이 바뀌면 그림이 다시 렌더링된다
- [ ] mermaid 문법 오류 시 원본 코드와 오류 메시지를 함께 보여주고 나머지 문서는 정상 렌더링된다
- [ ] 그림은 편집·내려받기 대상이 아니다. 고치려면 원본 MD의 코드블록을 고친다

#### R11 읽는 중 질의

근거: [[SYNC-RFQ-001#Q4]] · 사용자 결정 2026-09-22 — 맥락을 미리 싣는 대신 모델이 관계도를 따라 스스로 읽는다(ReAct) · 사용자 결정 2026-09-29 — 대화와 첨부를 서버에 보관한다

문서를 읽다가 그 자리에서 묻는다. 모델이 같은 프로젝트의 문서·항목·참조를 도구로 읽으며 답한다. **읽기를 돕는 것이지 쓰는 것이 아니다**(2장) — 대화는 프로젝트마다 보관되어 이어 갈 수 있고, 명세는 바꾸지 않는다.

처음(카드 U)에는 보고 있는 항목 본문과 직접 상위·하위의 이름만 실어 보냈다. 「근거가 뭐라고 했어」에 이름은 알고 내용은 모르는 답이 나왔다. 관계도는 이미 있으니 모델이 그것을 따라 읽게 한다.

- [ ] 보고 있는 **문서**가 시작 맥락이다 — 제목·상태·버전과 그 문서의 모든 항목 ID·이름. 항목은 힌트일 뿐이라 **고르지 않아도 묻는다**
- [ ] 모델은 같은 프로젝트를 **읽기 도구 다섯**(항목·참조·사슬·문서 목록·문서 전문)으로 읽는다. 프로젝트 밖은 없고, **쓰는 도구는 없다**
- [ ] 모델이 **무엇을 왜 읽는지**가 읽을 때마다 실시간으로 보이고, 답 아래에 실제로 읽은 것이 남는다
- [ ] 상한은 글자가 아니라 **도구 8번·전체 120초**다. 넘으면 그때까지 읽은 것으로 답한다
- [ ] **대화는 프로젝트마다 서버에 보관한다.** 한 프로젝트에 대화가 여럿이고, 새로고침하거나 다른 기기에서 열어도 이어 간다. 사람이 지울 때까지 남고, 프로젝트를 해제하면 함께 사라진다. 명세 표와는 분리된 표다 — 재구축(UC-S6)이 건드리지 않는다
- [ ] **질문에 파일을 붙인다** — 이미지(캡처·그림)·글자 파일(md·txt·csv·json·yaml)·PDF. 드래그앤드롭·붙여넣기·업로드 셋 다. 이미지는 모델이 그대로 보고, 글자·PDF는 모델이 읽기 도구로 필요할 때 읽는다(도구 여섯째). 첨부도 대화에 묶여 보관되고 대화와 함께 지워진다. 상한은 이미지 10MB · 글자·PDF 1MB · 한 질문에 8개
- [ ] 읽어도 없는 것은 **모른다고 답한다.** 지어내지 않는다 — 사슬의 빈 단계나 아직 없는 참조를 근거로 어느 명세 단계가 비어 있는지 말한다
- [ ] 모델 키는 **서버에 하나**다. 사람마다 넣지 않는다. 키가 없으면 이 기능이 화면에서 **보이지 않고** 나머지 화면은 그대로 돈다
- [ ] **코드 그래프(UI-17)에서도 묻는다** — 고른 함수(항목이 없어도)가 시작 맥락이고, 도구·상한·대화는 문서에서 묻는 것과 같다. 아무 함수도 안 골랐으면 그래프 전체(카드 BI). 그 함수의 코드를 보면서 묻는다 — 질문은 오른쪽 끝 열(카드 BN)

#### R12 프로젝트 소유

근거: [[SYNC-RFQ-001#Q6]] · #91

프로젝트를 등록한 사람이 그 프로젝트의 소유자다. 소유는 등록 시점에 정해지고 바뀌지 않는다. 소유자가 아닌 사람에게 그 프로젝트는 **없는 것**이다 — 역할이 아니라 소유로 가른다(2장).

- [ ] 프로젝트를 등록한 사람이 소유자다. 소유자는 한 명이고 옮기지도 나누지도 않는다
- [ ] 프로젝트 목록·상세·문서·항목·참조·그래프·이력·순서대로 읽기는 소유자에게만 보인다. 웹과 MCP 어느 입구든 같다
- [ ] 소유자가 아닌 사람이 주소나 ID를 직접 지정하면 **없는 것과 같은 답**을 받는다. 남의 프로젝트가 있다는 사실이 새지 않는다
- [ ] 관리(재구축·해제)도 소유자만 한다
- [ ] 에이전트 토큰은 발급자가 소유한 프로젝트만 연다([[#R9]])
- [ ] 폴링·webhook·저장소 push 처리는 소유와 무관하게 모든 프로젝트에 돈다 — 사람이 없는 배치다
- [ ] 커밋으로만 알려진 자리표시 계정은 소유자가 될 수 없다 — 로그인한 적이 없어 등록할 길이 없다

#### R13 코드 대조

근거: [[SYNC-RFQ-001#Q7]] · 사용자 결정 2026-09-30 — graphify로 호출 그래프를 만들고 명세의 「호출하는 것」과 대조한다

구현이 명세대로인지를 어림잡지 않고 **호출 그래프로 대조한다.** 코드 저장소의 코드를 graphify(tree-sitter, 모델 없음)로 읽어 함수와 호출을 뽑고 MINISPEC 항목에 잇는다. 명세가 말한 호출과 실제 호출의 차이를 사람·질문 탭의 모델·에이전트·검사기가 **같은 결과로** 본다.

- [ ] 코드가 바뀐 커밋을 받으면 서버가 호출 그래프를 다시 만든다. 저장소에 `graphify-out/graph.json`이 커밋되어 있으면 그것을 쓴다
- [ ] 명세 항목과 함수는 docstring 첫 줄의 항목 ID로 잇고, 없으면 이름(`Class.fn`)으로 잇는다
- [ ] graphify가 못 푸는 호출(변수에 담은 객체의 메서드)은 싱크독이 파이썬 코드에서 보강해 푼다. TS/JS 코드는 함수의 끝 줄과 graphify가 놓친 맨 위 함수·호출을 싱크독이 다시 읽어 채운다(카드 BL)
- [ ] 명세의 「호출하는 것」과 실제 호출을 셋으로 가른다 — 같음 · 코드만(명세에 빠진 호출) · 명세만(코드에 없는 호출)
- [ ] 저장소의 검사기(`check_calls`)가 같은 대조를 로컬에서 하고, 어긋남 0이 슬라이스 완료 조건이다
- [ ] 웹 문서 패널의 「코드」 탭과 관계도의 코드 층에서 보고, 질문 탭의 모델과 MCP 에이전트도 같은 그래프와 코드를 읽는다
- [ ] 코드 본문은 싱크독 DB에 두지 않는다 — 그래프를 만든 커밋의 저장소에서 읽는다
- [ ] 프로젝트의 함수 전부를 한 그림으로 본다 — 코드 구조로 묶은 커뮤니티로 접어 두고 펼쳐 가며 찾고, MINISPEC 항목이 있는 함수는 대조 상태(같음·코드만·명세만)가 붙어 코드 탭으로 이어진다
- [ ] 그림에서 고른 함수의 본문을 그 자리에서 읽는다 — MINISPEC 항목이 없는 함수도. 왼쪽 파일 트리(폴더 한 단씩 › 파일 › 함수)로도 짚어 찾고, 파일·폴더를 고르면 그 안 함수 노드가 그림에 펼쳐진다. 고른 함수가 어느 명세의 어느 항목인지 — 항목·근거(상위 참조)·하위 참조 — 가 코드 옆에 보인다. 그림만으로는 노드가 무엇인지 모른다(2026-10-01 피드백, 카드 BF·BG). 커뮤니티는 그래프를 만들 때 서버가 모델 없이 계산한다(2026-10-01 사용자 결정 — graphify의 강점은 노드를 보여주는 것이다)
- [ ] 함수와 명세의 고리는 MINISPEC만이 아니다 — docstring 첫 줄의 항목 ID면 어느 문서든(라우터·MCP 도구의 API 항목) 잇고, 화면 코드는 파일 첫 주석의 화면 ID(UI-N)를 그 파일의 함수 전부에 잇는다. 대조(같음·코드만·명세만)는 그대로 MINISPEC 항목에만 — 다른 항목은 「어느 명세의 무엇인가」만 답한다(2026-10-02 사용자 결정, 카드 BJ)
- [ ] 함수 단위 명세가 없는 층(리포지토리·스키마·마이그레이션·도구 등)은 클래스 명세의 층 표로 그 층의 명세에 이어진다 — 어느 층에도 안 걸리는 코드와 코드에 안 맞는 표 줄은 검사기가 잡는다(2026-10-02 사용자 결정, 카드 BM)

#### R14 서버 저장

근거: [[SYNC-RFQ-001#Q7]] · 사용자 결정 2026-09-30 — GitHub 없이 서버에 바로 저장한다. 저장 방식은 프로젝트를 만들 때 고른다. 코드는 하나이고 판은 설정으로 가른다

GitHub 저장소 없이도 쓴다. 프로젝트를 만들 때 **저장 방식**을 고른다 — GitHub 저장소 또는 **서버 저장소**(싱크독 서버 안의 git 저장소). 서버 저장소도 git이라 버전·되돌리기·재구축·코드 대조가 GitHub 프로젝트와 같다. 서버는 쓸 수 있는 저장 방식을 설정으로 켠다 — 인터넷판은 둘 다, 폐쇄망판은 서버 저장소만.

- [ ] 프로젝트를 만들 때 저장 방식을 고른다. 웹과 MCP 어느 입구든 같다
- [ ] 서버가 켠 방식만 고를 수 있다. 둘 다 켜진 서버에서는 에이전트가 사람에게 먼저 묻고 고른다 — MCP 도구가 저장 방식을 기본값 없이 받는다. 하나만 켜진 서버는 그것을 알려 준다
- [ ] 서버 저장소는 GitHub 토큰 없이 쓴다
- [ ] 서버 저장소에서도 골격 커밋·이력·되돌리기·상태·휴지통·재구축이 GitHub 프로젝트와 같다
- [ ] 서버 저장소는 코드를 두 길로 받는다 — **git push**(비밀번호 칸에 개인 토큰), 그리고 git이 없는 PC를 위한 **MCP 코드 올리기**(바뀐 파일과 지운 경로, 한 번 5MB·파일 500개, 명세 경로·비밀 꼴·이진 파일 거절). 코드 대조([[#R13]])가 GitHub 프로젝트와 같다
- [ ] 서버 저장소는 git으로 clone해 파일로 직접 읽을 수 있다(개인 토큰). 받는 것은 `main` 하나이고 이력을 뒤로 돌리거나 가지를 지우는 push는 거절한다
- [ ] 프로젝트를 해제하면 서버 저장소는 지우지 않고 보관 폴더로 옮긴다. 같은 코드로 「기존 명세 가져오기」를 고르면 되살아난다. 완전히 지우는 것은 서버 운영자가 폴더를 지워서다
- [ ] 서버 저장소는 서버 볼륨이 유일한 원본이다 — 백업은 운영자 몫이고 방법은 인프라 문서가 말한다
- [ ] 다른 곳의 git 저장소를 번들 파일 하나로 가져와 서버 저장 프로젝트로 등록한다 — 명세·버전·상태 이력은 커밋에서 되살아나고 대화·토큰은 오지 않는다. 싱크독_깃허브의 프로젝트를 싱크독_로컬로 옮기는 길이고, 두 판 모두 된다

#### R15 싱크독_로컬 — Rust 설치형

근거: [[SYNC-RFQ-001#Q7]] · 사용자 결정 2026-09-30 — 폐쇄망판은 요청자 혼자 쓰고 로그인이 없다 · [[SYNC-RFQ-001#Q8]] · 사용자 결정 2026-10-06 — 릴리즈 이름 둘(싱크독_깃허브·싱크독_로컬), 싱크독_로컬은 Rust 설치형 · 사용자 결정 2026-10-07 — 설치·자동 시작·데이터 자리·설정 자리·백업·속도 목표

인터넷이 없는 망에서도 쓰는 **싱크독_로컬**이다. 싱크독_깃허브와 **기능이 같고**(같은 화면·같은 API·같은 MCP 도구) 다른 것은 넷이다. 저장은 서버 저장소만([[#R14]]), 로그인이 없다(한 사람이 쓴다), 실행 중에 바깥으로 나가는 요청이 없다([[#N4]]), 그리고 **이 PC에 설치하는 프로그램**이다.

**릴리즈 이름은 둘이다**(2026-10-06) — 인터넷판은 **싱크독_깃허브**, 폐쇄망판은 **싱크독_로컬**. 사람과 에이전트가 보는 이름이다.

**명세 하나, 구현 둘**(2026-10-07) — 싱크독_깃허브는 파이썬(`backend/`), 싱크독_로컬은 Rust(`local/`)로 만든다. 요구·화면·API는 이 체인 하나를 함께 쓰고 구조·MINISPEC·구현 계획만 구현마다 둔다([[SYNC-INFRA-001]] C11). 화면은 같은 React 빌드를 담는다. Rust 판이 나오기 전까지는 파이썬 판을 설정(`EDITION=closed`)으로 돌리는 Docker 묶음이 이 이름을 쓴다([[SYNC-INFRA-001]] 8.1).

- [ ] 한 사람이 쓴다. 로그인 화면이 없고, 켜질 때 로컬 사용자 하나를 두어 모든 화면 요청을 그 사람으로 본다
- [ ] 에이전트(MCP)와 git은 싱크독_깃허브처럼 개인 토큰으로 막는다. 토큰은 설정에서 발급한다
- [ ] 저장 방식은 서버 저장소 하나다. GitHub 로그인·통지 경로는 없다
- [ ] 로그인이 없으므로 이 PC에서만 연다(127.0.0.1). 다른 이름으로 들어오는 요청과 다른 사이트가 보내는 쓰기 요청은 막는다
- [ ] 싱크독_깃허브와 같은 화면([[SYNC-UI-002]])과 같은 API([[SYNC-API-001]]·[[SYNC-API-002]])를 낸다 — 같은 시나리오 시험(공용 계약 시험)을 두 판이 다 통과한다
- [ ] 윈도는 설치 파일(setup.exe) 하나, 리눅스는 .deb와 AppImage로 설치한다. 데이터베이스(PostgreSQL)와 git을 함께 담아 따로 깔 것이 없다(.deb는 시스템 git을 쓴다). 서명은 없다 — 설치 때 「알 수 없는 게시자」 경고가 뜬다
- [ ] 로그인할 때 저절로 켜지고 트레이 아이콘에서 열고 끈다. 이미 켜져 있을 때 다시 실행하면 떠 있는 것을 브라우저로 연다. 저절로 켜지기는 끌 수 있다
- [ ] 데이터(DB·서버 저장소)는 사용자 폴더에 둔다 — 윈도 `%LOCALAPPDATA%\SyncDoc Local`, 리눅스 `~/.local/share/syncdoc-local`. 설정에서 다른 폴더로 옮길 수 있다
- [ ] 바꿀 값은 설정 창의 「이 PC」 묶음에서 바꾼다 — 모델 주소·키, 이름, 자동 시작, 데이터 자리, 백업. 같은 망에 여는 것처럼 위험한 값만 설정 파일에 둔다
- [ ] 하루 한 번 고른 폴더에 DB와 서버 저장소를 묶어 백업한다 — 최근 14개, 암호를 넣으면 암호화. 「지금 백업」과 「되살리기」가 있다
- [ ] 새 판은 덮어 설치한다. 데이터는 그대로이고 스키마는 켜질 때 올라간다
- [ ] 질문 탭의 모델은 사내 OpenAI 호환 주소를 쓴다. 주소를 넣지 않으면 탭이 없다
- [ ] 판 이름을 화면 상단 바·브라우저 탭 제목과 MCP 서버 이름이 말한다 — `syncdoc_github`·`syncdoc_local`. 에이전트에 둘을 같이 붙여도 헷갈리지 않는다
- [ ] 한 PC에서 두 판을 나란히 띄운다 — 싱크독_깃허브는 8000, 싱크독_로컬은 8010. 데이터·포트가 겹치지 않는다
- [ ] 빠르다 — 켜기 3초(설치 뒤 첫 실행 15초), 화면 조회 0.1초, 문서 저장(git 포함) 0.3초, 싱크독 크기 저장소의 코드 그래프 10초, 켜 둔 메모리 300MB(데이터베이스 포함). 같은 PC에서 싱크독_깃허브보다 느린 항목이 없다

### 3.2 비기능 요구사항

#### N1 성능
근거: [[SYNC-RFQ-001#Q4]]
- [ ] GitHub 변경이 1분 이내에 플랫폼에 반영된다
- [ ] 문서 1천 건, 참조 1만 건 규모에서 항목 참조 조회가 1초 이내다
- [ ] MCP 응답이 3초 이내다
- [ ] 웹 응답이 3초 이내다. **모델 호출([[#R11]])은 예외이며** 그동안 화면이 기다리고 있다고 말한다

#### N2 환경·접근
근거: [[SYNC-RFQ-001#Q4]]
- [ ] 노트북에서 서버를 띄우고 공개 주소(Cloudflare Tunnel)로 노출한다. 사람은 위치에 상관없이 접속한다
- [ ] 사람은 GitHub OAuth로, 에이전트는 발급 토큰으로 식별된다
- [ ] 로그인은 **허용한 GitHub 계정만** 된다(설정 `ALLOWED_LOGINS`, 비면 GitHub 계정이면 누구나). 목록 밖 계정은 새 로그인·이미 있는 세션·개인 토큰(MCP·git) 모두 막힌다. 보이는 것은 자기가 등록한 프로젝트뿐이다([[#R12]]). 저장소 쓰기 권한은 GitHub이 push에서 따로 가른다(카드 BP)
- [ ] 서버는 이 PC에만 포트를 연다(127.0.0.1). 바깥에서 들어오는 길은 공개 주소(Tunnel) 하나다
- [ ] 폐쇄망판([[#R15]])은 로그인이 없고 이 PC에서만 연다. 에이전트와 git은 개인 토큰으로 식별된다

#### N3 운영
근거: [[SYNC-RFQ-001#Q4]]
- [ ] 코드 저장소(GitHub 또는 서버 저장소)가 단일 진실 원천이다. 명세·상태·버전·참조는 저장소만으로 재구축된다
- [ ] 문서는 삭제하지 않는다 — **휴지통에 넣는다.** 잘못 만든 문서는 파일을 저장소에서 지우고(커밋) 행은 남긴 채 `휴지통` 표시를 한다. 참조하던 곳엔 `끊어진 참조`가 붙고, 되살리면 파일과 항목이 돌아오며 참조가 다시 이어진다. **완전 삭제**(행까지)는 휴지통 안에서만, 다른 문서가 더 이상 가리키지 않을 때만. 이력이 있는 문서를 하드 삭제로 잃는 길은 없다
- [ ] GitHub 프로젝트는 플랫폼이 꺼져 있어도 GitHub에서 문서를 읽고 쓸 수 있다. 서버 저장소는 플랫폼과 함께 돈다 — 대비책은 사람의 clone과 볼륨 백업이다([[#R14]])

#### N4 인터넷 없이 돈다
근거: [[SYNC-RFQ-001#Q7]]
- [ ] 싱크독_로컬은 실행 중에 바깥으로 나가는 요청이 없다 — 글꼴·스크립트·그림을 앱이 담는다. 화면 배치(iframe)가 문서 안에서 바깥 글꼴을 가리켜도 앱이 담은 것으로 바꾸고, 나머지 바깥 링크는 뺀다
- [ ] 반입은 설치 파일 하나로 한다(Rust 판 전까지의 Docker 판은 이미지 묶음 하나). 폐쇄망에서 빌드하거나 내려받지 않는다
- [ ] 업데이트는 새 설치 파일로 덮어 설치하면 된다(Docker 판은 새 묶음을 불러와 다시 띄운다). 데이터는 그대로이고 스키마는 켜질 때 올라간다

## 5. ID 체계

```
문서 ID     {프로젝트코드}-{타입}-{번호}      예) SYNC-PRD-001
항목 ID     {문서ID}#{항목번호}              예) SYNC-PRD-001#R12
참조 문법   [[항목ID]] 또는 [[문서ID]]   — 참조 대상은 항목이 기본이며, 문서 전체를 근거로 삼을 때만 문서 ID를 쓴다
```

| 순서 | 타입 코드 | 단계 | 항목 ID 예시 |
|---|---|---|---|
| 1 | RFQ | RFQ | `#Q01` |
| 2 | PRD | PRD | `#G1`(목표), `#R12`(요구사항) |
| 3 | SCN | 사용자 시나리오 | `#P1`(페르소나), `#S03`(시나리오) |
| 4 | UC | USECASE | `#UC05` |
| 5 | INFRA | 인프라 아키텍처 | `#C03`(컴포넌트) |
| 6 | DOM | 도메인·클래스·데이터 | `#D01`(개념), `#C03`(클래스), `#T02`(테이블) — 도메인 모델, 클래스 명세, ERD/DD를 이 단계에 둔다. 문서는 여럿일 수 있다 |
| 7 | UI | 화면 명세 | `#V07`(화면) |
| 8 | API | API 명세 | `#POST/orders` |
| 9 | SEQ | SEQUENCE | `#S01` |
| 10 | MS | MINISPEC | 문서 단위 |
| 11 | CODE | CODE | 커밋·PR URL |
| — | STD | 표준 (단계 밖) | 규칙 항목. 명세 작성 규약·뷰 규약. 대시보드 11칸에 안 나오고 프로젝트 상세에 별도 묶음. 싱크독 프로젝트에만 있고 다른 프로젝트는 이걸 그대로 쓴다 |

규칙
- 프로젝트 코드는 영문 대문자 4자 이내
- 항목 번호는 문서 안에서 유일하며, 삭제해도 회수하지 않는다
- 참조는 하위 → 상위 방향으로만 적는다. 역방향(누가 나를 참조하는가)은 시스템이 계산한다
- 순서 변경 이력: 인프라·도메인 단계를 거치며 클래스 명세와 ERD를 도메인 단계(6)에 합치고, 화면 명세를 독립 단계(7)로 분리했다. ERD를 따로 두면 클래스와 같은 것을 두 번 그리게 되기 때문이다
- 되돌아오는 문서: 클래스 명세(DOM-002)는 6단계에서 엔티티(v1)까지 쓰고, API(8) 뒤에 컨트롤(v2)을 채우고, SEQUENCE(9) 뒤에 시퀀스가 드러낸 구멍을 반영(v3)한다. **SEQUENCE의 완료 조건은 그 v3 완료다.** 단계 수는 11 그대로이며, DOM 단계가 v3까지 초안으로 남는 것은 정확한 표시다

## 6. 미결사항

**진행 중 결정**
- [x] MCP 쓰기 권한 범위 (전체 문서 vs 특정 프로젝트) — 결정: 묶지 않는다. 토큰은 발급자에게만 묶이고 그 사람이 보는 모든 프로젝트에 쓴다. 인프라 5장 "저장소 권한이 곧 접근 권한"과 같은 전제이고, 비목표에 역할·권한 관리가 있다. 나중에 좁혀야 하면 스키마 대신 저장 시점에 발급자의 저장소 권한을 확인한다 → **v2에서 [[#R12]]로 자연히 좁아졌다** — 토큰은 발급자가 소유한 프로젝트만 연다. 토큰에 범위를 두지 않고 스키마를 안 늘린다는 결정은 그대로다
- [x] 소유자 외 접근(공유·초대) — 결정: 지금은 없다. 여덟 프로젝트에 교차 작성이 한 건도 없었다. 필요해지면 `project_members` 표 하나와 게이트 조건 한 줄이면 된다 — 미리 만들지 않는다
- [x] 알림 방식 → 별도 알림 없음. 프로젝트 상세가 끊어진 참조·규약 오류·미완성을 직접 보여준다. 통보받을 상대가 자기 자신이라 그 이상은 없다([[SYNC-RFQ-001#Q6]])
