# 명세 작성 규약

이 문서 자체가 규약을 따른다. frontmatter가 위에 있고, 머리 표가 없고, 변경 이력 절이 없다.

## 0. 이 문서가 다루는 것

싱크독에 올라가는 명세 원본(MD)을 **어떻게 써야 하는지**. 읽는 사람은 에이전트다 — `get_template`이 이 문서와 타입별 템플릿을 돌려준다. 사람용 뷰를 어떻게 그리는지는 [[SYNC-STD-002]] 뷰 규약이 따로 다룬다.

PRD R1이 "원본 규약이 정의되고 위반 시 오류를 낸다"고만 했고 그 규약이 어디에도 없었다. 이 문서가 그것이다. UC-S1(규약 검증)과 항목 추출(SEQ-12), `display_name`(클래스 미결)이 여기에 의존한다.

**두 가지 판정**
- **규약 위반** — 저장이 거부된다. 시스템이 문서를 파싱할 수 없는 경우. 3장
- **미완성** — 저장은 되고 경고만. 필수 절이 없는 경우. 완료 조건에서 막힌다. 4장

초안은 미완성이어도 된다. 명세는 왔다갔다하며 쓰는 것이라 중간에 끊겨도 저장되어야 한다.

## 1. 공통 규약

### 1.1 파일

```
docs/specs/
├── _templates/          타입별 템플릿. 필수 절이 서브타입마다 다른 DOM·API는 **서브타입별 파일**(`DOM-도메인.md`·`DOM-클래스.md`·`DOM-ERD.md`·`API-REST.md`·`API-MCP.md`), `DOM.md`·`API.md`는 고르는 안내. **싱크독 저장소에만 있다** — 새 저장소는 사본 없이 README 링크로 본다(카드 AB·AG)
├── assets/              첨부. MD에서 상대 경로로
├── 01-RFQ/  SYNC-RFQ-001.md
├── 02-PRD/  SYNC-PRD-001.md
├── …                    (11단계. 번호는 2장 순서)
├── 11-CODE/ SYNC-CODE-001.md
└── STD/     SYNC-STD-001.md  SYNC-STD-002.md   ← 단계 밖이라 번호 없음
```

- 경로 `docs/specs/{NN-TYPE}/{doc_id}.md`. **디렉터리 이름은 `{2자리 단계번호}-{TYPE}`** — 저장소를 열었을 때 읽는 순서대로 보이게(2장 11단계). 단계 밖인 `STD`는 번호 없이 `STD/`
- 디렉터리의 `TYPE` 부분과 frontmatter `type`이 다르면 **위반**. 파일명과 frontmatter `doc_id`가 다르면 **위반**
- 문서 ID `{프로젝트코드}-{TYPE}-{NNN}`. 세 자리. 시스템이 발급(`create_document`)하며 에이전트는 비워도 된다. **완전 삭제된 문서의 번호는 다시 쓰일 수 있다** — 완전 삭제는 아무도 가리키지 않을 때만 되므로(PRD N3) 되살아날 참조가 없다. 휴지통에 있는 동안은 행이 남아 번호가 비지 않는다. 항목 ID와 다른 점이다
- **새 저장소에는 `_templates/`도 `STD/` 본문도 없다.** 초기화는 빈 단계 디렉터리와 `README.md`만 커밋하고, README가 싱크독 저장소의 규약·템플릿을 링크로 가리킨다. 에이전트는 MCP `get_template`으로 앱에 내장된 원본을 받는다([[SYNC-API-002#get_template]]). 사본을 복사하던 v1은 규약이 바뀌어도 갱신되지 않았다(#113·#129)
- **템플릿은 필수 절을 다 갖춘다.** 템플릿대로 쓰면 미완성 경고가 나지 않아야 한다 — `tools/check_templates.py`가 타입·서브타입마다 그 템플릿에 필수 절이 다 있는지, 항목 예시가 항목 패턴에 맞는지 본다(카드 AG). 템플릿이 타입당 하나이던 때 DOM은 도메인 모델 골격만 들어 있어, 그대로 쓴 클래스 명세·ERD가 **반드시** 미완성이 됐다(#114)
- **`_templates/`와 `assets/`는 명세 문서가 아니다.** 검사기도 파이프라인도 이 둘을 건너뛴다 — 템플릿은 `doc_id`가 빈 채로 있는 것이 정상이라, 세면 있지도 않은 위반이 잔뜩 뜬다([[SYNC-MS-009#git.list]]는 이미 거르는데 `validate.py`가 안 걸러 새 프로젝트에 돌리면 가짜 위반 12건이 떴다, #52)
- 인코딩 UTF-8, 줄바꿈 LF

### 1.2 frontmatter

문서 메타는 frontmatter에만 둔다. 본문에 머리 표를 두지 않는다 — 두 곳에 있으면 어긋난다.

| 필드 | 필수 | 형식 | 누가 채우나 |
|---|---|---|---|
| `doc_id` | ○ | `SYNC-PRD-001` | 시스템 (생성 시). 이후 변경 불가 |
| `type` | ○ | 11단계 타입 코드 또는 `STD` | 에이전트 |
| `title` | ○ | 한 줄 | 에이전트 |
| `status` | ○ | `draft` / `approved` — 초안·완료 | 생성 시 `draft`. 이후 사람이 웹에서. 완료 문서를 고치면 `draft`로 내려간다 |
| `upstream` | | 문서 ID 배열. 이 문서가 근거로 삼은 문서 | 에이전트 |

`status`가 진실이다. DB의 `documents.status`는 이 값의 사본이다. 웹에서 상태를 바꾸면 이 줄이 고쳐지고 커밋된다. **MCP로 이 값을 바꿔 보내면 위반이다** — 상태 변경은 사람이 웹에서만 한다(UC-H8). GitHub에 직접 push한 경우는 원본이 진실이므로 그대로 받는다.

`downstream`(누가 나를 참조하나)은 frontmatter에 없다. 시스템이 참조 테이블에서 계산해 뷰에 보여준다. 여기 두면 하위 문서가 생길 때마다 상위 문서에 커밋이 생겨 변경 감지가 연쇄로 돈다.

`upstream`은 **문서 단위 참조**다. 본문의 `[[ ]]`가 항목 단위 참조고, 이건 "이 문서 전체가 저 문서를 전제로 한다"는 뜻. 둘 다 참조 테이블에 들어간다.

**위반**: 필수 필드 누락, `type`이 목록에 없음, `status`가 둘 중 하나가 아님, `doc_id` 형식 불일치.

### 1.3 항목

**항목 = ID로 시작하는 헤딩.** 레벨은 상관없다.

```markdown
#### R12 참조 문법          ← 항목. ID=R12, 제목=참조 문법
## 2. 요구사항              ← 절. 첫 토큰 "2."는 ID 패턴이 아님
#### 인수기준               ← 절. ID가 없음
```

- 헤딩의 **첫 토큰**이 그 타입에 허용된 ID 패턴(2장)과 맞으면 항목이다. ID 뒤에 마침표·콜론을 붙이지 않는다. `#### R1. 제목`은 첫 토큰이 `R1.`이라 항목이 아니다
- 항목 ID는 문서 안에서 유일하다. 중복이면 **위반**
- 삭제된 ID는 재사용하지 않는다. 다시 쓰면 **위반** (UC-S1 2b)
- 번호에 패딩을 두지 않는다. `R1`, `R12`. `R01`은 **위반**
- 제목은 ID 다음 공백 뒤 나머지 전부. `display_name`이 된다
- **항목 블록** = 그 헤딩부터, 같은 레벨 이상의 다음 헤딩 직전까지. 더 낮은 레벨 헤딩은 블록 안에 포함된다

```markdown
#### R12 참조 문법          ┐
본문 …                      │ R12 블록
##### 인수기준              │ (##### 는 더 낮으니 포함)
- [ ] …                     ┘
#### R13 버전               ← 여기서 R12 블록 끝
```

- 하위 항목은 없다. `R12`의 세부는 헤딩이 아니라 블록 안 본문·표·목록으로 쓴다
- **표 행은 항목이 아니다.** `| R12 | … |`는 참조 대상이 못 된다. 참조돼야 하면 헤딩으로 쓴다. 표가 읽기 편한 건 뷰가 헤딩들을 모아 표로 만든다

### 1.4 참조

- 문서: `[[SYNC-PRD-001]]` · 항목: `[[SYNC-PRD-001#R12]]` · **같은 문서 안 항목: `[[#R12]]`** (문서 ID 생략)
- 방향은 **하위 → 상위**로만 적는다. 이 문서가 근거로 삼는 것을 적는다. 역방향(누가 나를 참조하나)은 시스템이 계산한다
- **연관은 글이 아니라 참조로 적는다.** "연관: R5"라고 쓰면 시스템이 못 읽는다. `[[SYNC-PRD-001#R5]]`라고 써야 시스템이 R5와 이 항목을 잇는다 — 뷰에서 건너가고, R5가 사라지면 이 항목에 끊어진 참조가 표시된다. 유스케이스의 포함·확장점, 시퀀스의 근거 유스케이스, 화면의 주 유스케이스, 제약의 출처 — 전부 참조다
- 대상이 아직 없어도 저장된다. `미존재` 표시가 붙고, 대상이 생기면 다음 저장 때 풀린다 (UC-S2 2a)
- 코드블록·인라인 코드(백틱) 안의 `[[ ]]`는 참조로 보지 않는다. 규약 문서처럼 문법을 설명할 때 쓴다
- 항목 ID에 `/`·`{}`가 있으면(`POST/api/docs/{docId}`) 그대로 쓴다. `[[SYNC-API-001#POST/api/docs/{docId}]]`. 항목 ID 부분은 공백만 없으면 된다

**위반**: `[[ ]]` 안이 문서 ID 형식이 아님.

### 1.5 코드블록

| 언어 태그 | 용도 | 뷰가 하는 것 |
|---|---|---|
| `mermaid` | 다이어그램 전부 (클래스·ERD·시퀀스·플로우) | 그림으로 렌더링 |
| `yaml` | OpenAPI 조각 등 | 구문 강조 |
| `json` | MCP 도구 스키마 등 | 구문 강조 |
| `html` | 와이어프레임 뼈대 | 배치로 렌더링 |
| `markdown` | 예시 | 그대로 |
| 그 외 | 코드 | 구문 강조 |

- mermaid 문법 오류는 **위반이 아니다.** 저장되고 뷰가 오류를 표시한다 (UC-H2 2a)
- 코드블록은 **항목이 될 수 없다.** 코드블록 안 내용을 참조하려면 코드블록 앞에 항목 헤딩을 둔다

```markdown
#### POST/api/docs/{docId}/revert 되돌리기     ← 항목
```yaml
post: { summary: … }                          ← 이 항목의 정의
```
```

이 규칙 때문에 **OpenAPI 전체를 코드블록 하나로 두는 방식은 못 쓴다.** 엔드포인트마다 헤딩 + yaml 조각이다. 클래스도 묶음 다이어그램 하나가 아니라 클래스마다 헤딩 + 작은 다이어그램이다. 대신 뷰가 조각들을 모아 전체 그림을 그린다.

### 1.6 절

- 절 = 항목이 아닌 헤딩. **절 헤딩에는 번호를 붙인다** (`## 1.`, `### 2.3`). 첫 토큰이 숫자면 절대 항목이 될 수 없으므로, 영문 단어형 ID 패턴(DOM·MS·MCP)에서 절 제목이 항목으로 오인되는 걸 막는다. 항목 블록 안의 소제목(`##### 인수기준`)은 번호 없이 한글로 쓴다
- 타입마다 **필수 절**이 있다(2장). 판정: 레벨 무관, 헤딩 텍스트에서 번호를 뗀 것이 필수 절 이름으로 **시작**하면 있는 것. `## 1. 목표 / 비목표`는 "목표"로, `## 2. 비목표`는 "비목표"로 통과. `## 3. 시나리오 ↔ 요구사항 대응표`는 "시나리오"로 시작하므로 `대응표` 절로 인정되지 않는다
- 필수 절 누락은 **미완성**. 저장되고 경고 표시. `approved`로 바꿀 때 막힌다
- 권장 절은 판정하지 않는다. 템플릿에만 있다

### 1.7 두지 않는 것

| 두지 않음 | 대신 |
|---|---|
| 본문 머리 표 (문서 ID·상태·작성일…) | frontmatter. 뷰가 표로 그린다 |
| 변경 이력 절 ("vX에서 바뀐 것") | 커밋 메시지. 첫 줄 요약, 둘째 줄부터 이유. UI-7이 보여준다 |
| 작성일·작성자 | 커밋 |
| 버전 번호 | DB·커밋. 본문에 안 적는다 |
| 하위 항목 헤딩 (`R12-a`) | 블록 안 본문 |
| 표 행 항목 | 헤딩 |

### 1.8 작업 단위 — 문서 하나

에이전트는 **문서 하나를 만들거나 고치면 멈춘다.** 결과를 사람에게 전하고 웹(UI-5)에서 읽으라고 한 뒤, 사람이 「다음」이라고 하기 전에는 다음 문서를 만들지 않는다. 같은 단계에 문서가 여럿이어도(DOM 셋·UI 둘·API 둘) 같다 — **단계가 아니라 문서가 단위다.**

**왜.** 명세는 대화의 결과다([[SYNC-SCN-001#S1]]·[[SYNC-SCN-001#S2]]). 한 단계를 통째로 채우면 사람이 읽기 전에 앞 문서의 예측 위에 뒤 문서가 쌓이고, 앞 문서를 고치는 순간 그 예측이 전부 `확인 필요`가 된다. 시스템은 이것을 막지 않는다([[SYNC-PRD-001#R6]] — 상태는 신호다). 대신 `create_document`·`update_document`의 결과에 `next_step` 한 문장이 실려 온다 — 에이전트는 그 문장을 사람에게 그대로 전하고 멈춘다. 실제로 한 프로젝트에서 DOM 셋이 한 대화에 한꺼번에 생겼다 — 이 절이 없어서였다.

DOM 셋은 사이에 **다른 단계가 끼는** 순서가 있다(2.6). 그것만은 시스템이 막는다.

### 1.9 코드 구조

명세가 코드의 모양까지 정한다. **기본형은 도메인별 폴더 + 계층 파일**이고, 그 프로젝트의 확정본은 클래스 명세(2.6)의 「폴더 구조」 절이다.

**저장소 루트부터.** 저장소 하나가 프로젝트 하나다(1.1). 서버와 화면은 **폴더를 따로 둔다** — 언어도 빌드도 다르고, 한 폴더에 섞으면 의존성 파일이 서로를 덮는다.

```
<저장소>/
├── backend/                서버. 아래 app/ 기본형
├── frontend/               화면. 빌드 결과가 어디로 가는지는 클래스 명세에 적는다
├── docs/specs/             명세 원본. 양쪽이 같이 본다
├── tools/ · scripts/       검사기 · 기동 스크립트
├── Dockerfile · docker-compose.yml   배치
├── .env.example            필요한 환경 변수의 이름만. 값은 비운다
├── .gitignore · .dockerignore
└── README.md · AGENTS.md   사람용 · 에이전트용
```

서버가 없는 프로젝트는 `backend/`가 없고, 화면이 없으면 `frontend/`가 없다. 하나뿐이어도 **루트에 바로 쏟지 않는다** — 나중에 다른 하나가 생길 때 전부 옮겨야 한다.

```
app/
├── main.py              앱 조립·라우터 등록
├── core/                설정·DB 세션·에러 — 도메인에 속하지 않는 것
├── domains/<도메인>/
│   ├── router.py        HTTP 입출력만. 비즈니스 판단·DB 접근 금지
│   ├── schemas.py       요청·응답 모델만
│   ├── service.py       비즈니스 로직. 트랜잭션 경계가 여기
│   ├── crud.py          DB 접근만. 예외 응답 생성 금지
│   ├── models.py        ORM 정의만
│   ├── ports.py         (조건부) 외부 연동 인터페이스
│   └── adapters/        (조건부) 그 구현
├── infra/               외부 연동 공용 클라이언트
└── shared/              여러 도메인이 쓰는 순수 유틸
tests/                   app/ 구조를 그대로 (거울)
```

- **호출 방향은 `router → service → crud` 한 방향이다.** 역방향·건너뛰기 금지, 한 파일에 두 계층을 섞지 않는다. 계층을 지키기 어려운 코드가 나오면 그 자리에서 파일을 나눈다 — 「일단 여기 두고 나중에」는 하지 않는다
- **도메인 경계는 도메인 모델(DOM 도메인 모델 문서)이 정한다.** 폴더를 새로 만들려면 도메인 모델부터 고치고 클래스 명세가 뒤따른다
- **`ports.py`·`adapters/`는 조건부다** — 외부 API·큐·파일 스토리지·LLM 호출이 실제로 있을 때만 그 도메인 안에 둔다. 「나중에 DB를 바꿀 수도 있으니까」는 이유가 아니다
- **과설계 금지** — 사용처가 한 곳뿐인 추상화(베이스 클래스·제네릭·팩토리)는 두 번째 구현체가 실제로 생길 때 만든다. 지금 요구에 없는 미래 대비 코드를 두지 않는다
- **기본형에서 벗어나려면 클래스 명세 「폴더 구조」 절에 이유를 적는다**(2.6). 보는 것은 폴더의 **역할**이지 이름이 아니다 — `infra`를 `infrastructure`로 부르는 것은 벗어남이 아니다

**라우터를 도메인 밖으로 낼지는 입구의 수가 정한다.** 취향이 아니다.

| 입구 | 라우터 자리 |
|---|---|
| 하나 (웹 REST만) | 도메인 안. `domains/<도메인>/router.py` |
| 둘 이상이 **같은 쓰기 경로**를 탄다 | 도메인 밖. 입구마다 폴더 하나(`web/` · `mcp/` · `cli/`) |

입구가 둘인데 라우터를 도메인마다 두면 공통 저장 절차를 놓을 자리가 없어 같은 절차가 여러 벌로 갈라진다. 하나를 고치면 나머지가 조용히 어긋난다. 반대로 **「나중에 CLI를 붙일지도 모르니까」는 이유가 아니다** — 두 번째 입구가 실제로 생길 때 옮긴다. 입구를 밖으로 내도 `crud`는 **도메인 안에 남는다**. crud를 한곳에 모으면 어느 테이블이 어느 도메인 것인지 파일 위치로 알 수 없게 된다.

**프런트엔드 기본형.**

```
frontend/
├── index.html
├── src/
│   ├── main.tsx        진입
│   ├── App.tsx         라우팅
│   ├── pages/          화면 하나 = 파일 하나. 와이어프레임 항목과 1:1
│   ├── components/     두 화면 이상이 쓰는 조각만
│   ├── api/            서버 호출. 화면이 직접 fetch 하지 않는다
│   ├── assets/         번들에 들어가는 이미지·폰트
│   └── styles.css      UI 명세 3장 토큰의 전사. 값을 컴포넌트에 직접 쓰지 않는다
└── public/             그대로 서빙되는 것
```

호출 방향은 `pages → api → 서버` 한 방향이다. 백엔드의 `router → service → crud`와 같은 이유다 — 화면이 직접 요청을 짜면 주소와 응답 형태가 화면마다 흩어진다.

**설정 파일은 자기가 설정하는 것 옆에 둔다.**

| 무엇을 설정하나 | 어디에 | 예 |
|---|---|---|
| 저장소 전체 | 루트 | `Dockerfile` · `docker-compose.yml` · `.env.example` · `.gitignore` · `.dockerignore` · CI 설정 |
| 서버만 | `backend/` | `pyproject.toml` · `alembic.ini` |
| 화면만 | `frontend/` | `package.json` · `tsconfig.json` · 번들러 설정 |

- **`.env`는 커밋하지 않는다. `.env.example`만 커밋한다** — 이름과 설명만 적고 값은 비운다. 토큰·비밀번호가 저장소에 들어가는 경로가 여기다
- 같은 종류가 여럿이면 **뒤에 용도를 붙인다** — `Dockerfile.web` · `docker-compose.prod.yml`. 접미사 없는 것이 기본이다
- 설정 파일이 무엇을 읽는지는 **클래스 명세가 아니라 인프라 문서**가 정한다. 폴더 구조 절에는 자리만 적는다

**왜 이 장인가.** 1장은 `get_template`이 에이전트에게 통째로 내려주는 유일한 규약이다([[SYNC-API-002#get_template]]). 개발 규약(STD-004)에 적으면 싱크독 안에서만 유효하다 — 실제로 프로젝트마다 구조가 갈렸고, **갈린 이유를 아무도 적지 않았다.**

**싱크독 자신은 이 기본형이 아니다** — 입구가 둘이고([[SYNC-INFRA-001#C3]]) 그 둘이 같은 저장 파이프라인을 타야 해서([[SYNC-INFRA-001#C4]]) 라우터를 도메인 밖에 뒀다. 그 이유는 [[SYNC-DOM-002]] 1장에 적혀 있다. 규약을 만든 쪽이 먼저 지킨다.

### 1.10 커밋·PR에 에이전트 표시를 남기지 않는다

`Co-Authored-By: Claude …`, `Claude-Session: …`, 「Generated with Claude Code」 같은 줄을 **커밋 메시지에도 PR 본문에도 넣지 않는다.** 작성자는 사람의 GitHub 계정이다. 저장소의 contributor 목록과 커밋 이력에 도구가 드러나지 않게 하기 위해서다(사용자 결정 2026-09-22). 명세를 올리는 저장소와 싱크독 자신의 저장소([[SYNC-STD-004#DEV-15]]) 둘 다다.

이미 남은 이력은 그대로 둔다 — 이력을 다시 쓰지 않는다. 추적이 필요하면 이슈·PR 본문·CODE 카드의 완료란(커밋 범위)이 그 자리다.

## 2. 타입별 구조

11단계 타입마다 항목 ID 패턴, 필수 절, 권장 절, 항목 블록 안 구조. **우리가 실제로 쓴 13개 문서에서 뽑았다.** 이 표와 다르면 문서를 고친다(6장).

패턴은 정규식. 헤딩 첫 토큰이 이 중 하나에 맞으면 항목.

### 2.1 RFQ — 요구·인터뷰

| | |
|---|---|
| 항목 패턴 | `Q\d+` (요구 항목) |
| 필수 절 | 배경 · 요구 · 사용자와 환경 · 미정 |
| 권장 절 | 명세 체인 · 첫 프로젝트 |
| 항목 블록 | 요구 한 문단. 고객이 말한 것만. 제안·판단은 안 넣는다 |

### 2.2 PRD — 제품 요구

| | |
|---|---|
| 항목 패턴 | `G\d+` 목표 · `R\d+` 기능 요구 · `N\d+` 비기능 요구 |
| 필수 절 | 목표 · 비목표 · 요구사항 · 성공지표 · 미결사항 |
| 권장 절 | ID 체계 (프로젝트 첫 PRD에만) |
| 항목 블록 | `G`: 한 줄. `R`·`N`: 설명 문단 + 인수기준 체크리스트(`- [ ]`) |

`목표`는 표가 아니라 항목 헤딩 7개다. 지금 PRD-001의 표는 고쳐야 한다(6장).

### 2.3 SCN — 사용자 시나리오

| | |
|---|---|
| 항목 패턴 | `P\d+` 페르소나 · `S\d+` 시나리오 |
| 필수 절 | 페르소나 · 시나리오 · 대응표 |
| 권장 절 | 범위와 전제 |
| 항목 블록 | `P`: 역할·겪는 문제·원하는 것. `S`: 주체·상황 + 번호 흐름 + 변형 + 성공 조건 + 연관 요구사항 |

### 2.4 UC — 유스케이스 (Cockburn)

| | |
|---|---|
| 항목 패턴 | `UC-[AHGS]\d+` (A 에이전트 · H 사람 · G GitHub · S 하위기능) |
| 필수 절 | 액터 · 사용자 목표 수준 유스케이스 · 하위기능 수준 유스케이스 · 대응표 |
| 권장 절 | 형식 설명 |
| 항목 블록 | 표 12행(범위·수준·주 액터·이해관계자·사전조건·최소 보장·성공 보장·트리거·패키지·포함·확장점·일반화) + **기본 흐름** 번호 목록 + **확장** (`3a.` 형식) |

항목 안의 표는 **항목 블록 내부 구조**라 표여도 된다. 표 행이 항목이 아니면 표는 자유다.

### 2.5 INFRA — 인프라 아키텍처

| | |
|---|---|
| 항목 패턴 | `C\d+` 제약 |
| 필수 절 | 제약 · 구성도 · 기술 스택 · 데이터가 사는 곳 · 인증과 접근 · 미결사항 |
| 권장 절 | 내부 구조 · 외부 변경 감지 · 배치와 운영 |
| 항목 블록 | 제약 한 줄 + 출처 |

### 2.6 DOM — 도메인·클래스·데이터 (문서 셋)

세 문서가 같은 단계에 있고 항목 ID를 **이름으로** 맞춘다. 도메인 `Document`, 클래스 `Document`, 테이블 `documents`. 그래야 셋이 서로 참조된다.

**셋은 순서가 있고, 사이에 다른 단계가 낀다.** 같은 칸이지만 한 번에 쓰는 것이 아니다 — 싱크독 자신이 그렇게 썼다([[SYNC-DOM-002]]의 `upstream`이 [[SYNC-API-001]]·[[SYNC-API-002]]다). 한 칸에 모은 것은 그림이 같아서지 순서가 같아서가 아니다([[SYNC-RFQ-001]] 2장).

| 문서 | 언제 | 앞에 있어야 하는 것 — 없으면 `precondition-unmet` |
|---|---|---|
| 도메인 모델 | 6단계에서. UC·INFRA 뒤 | — |
| 클래스 명세 | **8 API 뒤에 돌아와서.** 클래스의 메서드는 API가 정한다 | 같은 프로젝트에 API 문서(REST든 MCP든) |
| ERD·DD | 클래스 명세 뒤. 테이블은 엔티티 클래스에서 나온다 | 같은 프로젝트에 클래스 명세 |

`create_document`(MCP)만 검사한다 — **존재**로 판정하고 상태는 안 본다([[SYNC-PRD-001#R6]]). GitHub push는 원본이 진실이라 그대로 받는다. 어느 문서인지는 `title`의 키워드로 안다 — **DOM 제목에는 「도메인」「클래스」「ERD」 중 하나가 들어가야 한다**(`frontmatter.title.subtype` 위반). 키워드가 없으면 그동안 필수 절 검사도 조용히 건너뛰었다.

**도메인 모델**
| | |
|---|---|
| 항목 패턴 | `[A-Z][A-Za-z]+` 개념 영문명. 헤딩 `#### Document 문서` |
| 필수 절 | 개념 식별 · 개념 모델 · 개념별 정리 · 경계 · 미결사항 |
| 항목 블록 | 속성 목록 + 관계 + 판정 근거 |

**클래스 명세**
| | |
|---|---|
| 항목 패턴 | `[A-Z][A-Za-z]+` 클래스명 (엔티티·서비스 모두) |
| 필수 절 | 폴더 구조 · 엔티티 · 의존 관계 · 설계 클래스 · 미결사항 |
| 항목 블록 | 클래스마다 헤딩 + mermaid classDiagram(그 클래스만) + 메서드 표 + 규칙 |

「폴더 구조」 절에는 **트리 + 폴더마다 한 줄**을 적고, 1.9 기본형과 다른 점이 있으면 **왜 다른지**를 함께 적는다(인프라 제약을 인용). 「의도는 4계층이다」처럼 결과만 적으면 다음 사람이 그 구조를 따라야 하는지 고쳐야 하는지 모른다.

**저장소 루트부터 적는다** — 서버 폴더 안만 적고 화면·설정 파일을 빼면 다음 사람이 그것들을 둘 자리를 다시 정한다. 화면이 있으면 `frontend/` 트리도, 빌드 결과가 어디로 가는지도 적는다. 서버 코드가 아직 없는 단계여도 루트는 적는다.

**ERD·DD**
| | |
|---|---|
| 항목 패턴 | `[a-z][a-z0-9_]+` 테이블명 |
| 필수 절 | ERD · DD · 인덱스 · 미결사항 |
| 항목 블록 | 테이블마다 헤딩 + 클래스 참조 + 컬럼 표 |

**템플릿은 셋이 따로다**(카드 AG) — `DOM-도메인.md`·`DOM-클래스.md`·`DOM-ERD.md`. 필수 절이 미결사항 말고는 하나도 겹치지 않아 한 파일로는 셋을 못 가르친다. 에이전트는 `get_template(…, "DOM", subtype="클래스")`처럼 **무엇을 쓸지 말하고** 받는다. 서브타입 없이 부르면 필수 절이 비어 오고 고르는 안내(`DOM.md`)가 온다.

지금 클래스 명세는 묶음 다이어그램에 클래스 여럿이 들어 있어 클래스가 항목이 아니다. 고쳐야 한다(6장).

### 2.7 UI — 화면 (문서 하나 또는 둘)

화면 설계와 와이어프레임을 **한 문서에 써도 되고 둘로 나눠도 된다.** 어느 쪽이든 규약은 하나다.

| | |
|---|---|
| 제목 | 「화면 설계」「와이어프레임」 중 하나가 들어가야 한다(`frontmatter.title.subtype` 위반, 3장). **문서가 둘이면 제목에 하나씩** — 검사기가 제목으로 파일을 고르는 자리가 있어(`check_tokens.py`는 「화면 설계」로 찾는다) 둘 다 넣으면 어느 쪽을 볼지 모른다. 어느 키워드든 아래 같은 규약이다 |
| 항목 패턴 | `UI-\d+` 화면. **헤딩 단계 무관** — `##`부터 `#####`까지 어디에 있어도 항목이다. 화면 헤딩은 그 안 소제목보다 상위여야 블록이 안 끊긴다 |
| 필수 절 | 미결사항 (11타입 공통) |
| 권장 절 | 이 문서가 다루는 것 · 유스케이스 대응 · 화면 목록 · 공통 틀 · 화면 흐름 |
| 항목 블록 — 필수 | **배치** html 코드블록 **하나**. 뷰도 검사기도 **첫 블록만** 본다 — 상태가 여럿이면 블록을 나누지 말고 그 한 블록 안에 보드를 세로로 쌓는다(아래 「상태 여럿」). **자기 완결** — `<style>`·`<link>`(폰트)를 안에 품는다. 공통 스타일을 「공통 틀」 절에 뺐다면 **공통 틀 블록 + 이 블록을 합친 것**이 자기 완결이다 |
| 공통 틀 | 「공통 틀」 절(이름으로 찾는다, 번호 접두 허용)의 **첫 html 블록**은 그 문서 **모든 화면 앞에 함께** 들어간다 — 공통 `<style>`·`<link>`·공통 부품 |
| 이미지·폰트 파일 | `docs/specs/assets/`에 두고 **문서 폴더 기준 상대 경로**(`../assets/x.png`)로 쓴다. 앱이 `GET /api/projects/{code}/files/{path}`로 준다([[SYNC-API-001]]) |
| 항목 블록 — 있으면 쓴다 | 한 줄 목적(종류·주 유스케이스·진입·이탈) · 메타 표 · **요소** 표 · **규칙** · **시나리오**. 소제목 이름은 「배치」「요소」「규칙」「시나리오」, 단계는 자유 |
| 요소 표 | `#` 열은 배치의 `data-el`과 같은 번호를 쓰되 **부분집합이어도 된다** — 설명할 것만 적는다. 표에 없는 번호는 배지만 붙는다. 반대로 **표에만 있는 번호**는 가리키는 것이 없으므로 검사기가 알린다. 한 칸에 번호를 둘 적지 않는다(`3·5`) — 검사기가 못 읽는다 |
| `data-el` 붙이는 곳 | `div`·`span` 같은 **보통 요소**에 붙인다. 표 행(`<tr>`)·svg 도형·입력칸(`<input>`·`<select>`·`<textarea>`)에는 배지가 그려지지 않아 **뷰가 위치를 재서 얹어 준다** — 보이기는 하지만 감싸는 요소에 붙이는 쪽이 정확하다. 검사기가 이런 자리를 알린다 |
| 상태 여럿 | 한 화면에 상태가 여럿이면(탭 전환·대화상자·배너·빈 상태) 주 아트보드 **아래에 작은 보드로 잇고** 그 앞에 회색 주석 한 줄을 둔다. 주석은 화면이 아니라 문서의 말이다. 번호는 상태를 가로질러 한 벌이다 |
| 대화상자 | 다른 화면 위에 뜨는 것은 **덮는 화면째** 그린다 — 낮은 아트보드에 흐린 배경과 오버레이를 깔고 그 위에 대화상자. 대화상자만 그려도 되지만 그러면 어디에 뜨는지 안 보인다 |
| 디자인 토큰 | 색·글꼴·간격 값을 문서로 정하려면 `## 3. 디자인 토큰` 장에 `### 3.1 색` · `### 3.2 타이포` · `### 3.3 간격·모서리·겹침·그림자`로 적는다 — `check_tokens.py`가 그 장·절 번호와 불릿 이름(`간격`·`모서리`·`겹침`·`그림자`)을 **글자 그대로** 찾아 CSS의 `:root`와 대조한다. 이 장이 없으면 그 검사는 돌지 않는다 |
| 뷰 | 렌더러 하나. 화면마다 **html 블록이 있으면** 배치를 **iframe으로 격리해 그대로** 그리고(사이트 CSS가 안 스며든다), **없으면** 설계만 있는 화면으로 표 한 행([[SYNC-STD-002]] V-UI). **배치가 본문 폭을 다 쓴다** — 요소 표·규칙·시나리오는 그 아래에 쌓인다. 권장 크기 1280×800이면 넓은 창에서 1:1로 보이고, 좁으면 축소되며 배치 위 「전체보기」로 언제든 1:1 |

요소 번호(`7.1`)는 항목이 아니다. 화면(`UI-5`)이 항목이고 요소는 그 안이다. 하위 문서(API·SEQ·MS)는 화면 ID로 참조하고 요소 번호는 산문에 적는다.

**만드는 법.** 에이전트가 가진 디자인 도구(클로드의 Artifact **Design 타입**, GPT·Gemini의 디자인 기능 등)로 화면을 만들고, 스타일까지 든 **자기 완결 html**(`<style>`·`<link>` 포함)을 `## UI-N` 아래 ```html 블록에 **그대로** 넣는다. 뷰가 iframe으로 격리해 그리므로 사이트 CSS와 안 부딪히고 모양이 그대로다. **도구가 없으면 직접 쓴 자기 완결 html도 된다** — 싱크독 12화면을 다시 그린 에이전트 둘 중 하나가 그랬다. 클로드 디자인 캔버스에서 그릴 때는 스타일을 **클래스로 `<helmet>`의 `<style>`에** 쓰고, 옮길 때 아트보드의 `<x-dc>` 안 html과 그 `<style>`을 꺼내 넣는다 — 인라인 `style=""`로 그리면 문서가 인라인 스타일 덩어리가 된다. 권장 크기 1280×800 — 배치가 본문 폭을 다 쓰므로 넓은 창에서는 줄지 않고, 좁은 창에서만 축소된다(배치 위 「전체보기」로 1:1). `data-el` 번호는 요소 표와 이으려면 붙이고, 아니면 없어도 된다. 회색 상자 뼈대를 손으로 그릴 이유가 없다 — 그건 도구가 없던 때의 모양이다.

**왜 이렇게 바꿨나 (카드 X, #94).** v1은 화면 설계(`#### UI-N`, 산문)와 와이어프레임(`## UI-N`, html)을 다른 문서로 두고 필수 절도 따로 두었다. 써 보니 에이전트가 화면을 와이어프레임 하나로 뽑아 오는데, 그것을 그대로 올리면 뷰가 비거나 html이 버려졌다 — 문서가 틀린 게 아니라 렌더러가 `## UI-N` 2단계와 `### 배치` 문자열을 고정하고, 검사기가 `^## (UI-\d+)`만 읽고, 템플릿이 `#### UI-1` 아래 `### 배치`를 두어 항목 블록을 스스로 끊고 있었다. 다른 프로젝트의 화면 문서 여덟은 **손대지 않는다** — 규약을 문서에 맞췄다.

**왜 또 바꿨나 (카드 AE, #127·#128·#132).** 새 에이전트 둘이 이 절만 보고 12화면과 HB 화면을 그린 뒤 막힌 곳을 보고해 왔다. 공통점은 하나였다 — 이 절이 **무엇을 그릴지**는 말하면서 **통과하려면 지켜야 할 기계적 제약**은 말하지 않았다. 번호를 어디에 붙일 수 있나, 블록은 몇 개인가, 표는 전부 적어야 하나, 제목 낱말이 파일 선택에 쓰인다는 것. 전부 코드에만 있었다. 그래서 위 표에 일곱 행을 더하고, 검사기 쪽도 **못 본 것을 통과로 내지 않게** 고쳤다 — 제목에 두 낱말을 다 넣고 문서를 둘로 나누면 검사기가 화면을 하나도 못 찾은 채 「통과」를 내고 있었다.

**왜 또 바꿨나 (카드 Z, #118).** 새 프로젝트 온보딩 시험(HB)에서 에이전트가 템플릿 예시대로 회색 상자 와이어프레임을 그렸고, 그마저 `class="topbar"`가 사이트 CSS에 먹혀 흰 글씨가 됐다. 뷰가 배치 html을 페이지 DOM에 직접 넣었고, `data-el` 요소마다 점선 테두리·흰 배경을 강제했고, 렌더러 안에 싱크독 자신의 클래스 사전 140줄이 박혀 있었다. 디자인 도구가 만든 페이지를 「그대로」 올리려면 셋 다 걷어야 했다 — 격리(iframe), 배지만, 스타일은 문서가 든다.

### 2.8 API — 인터페이스 (문서 둘)

**API 제목에는 「REST」「MCP」 중 하나가 들어가야 한다**(`frontmatter.title.subtype` 위반, 3장). 「에이전트 도구」 같은 제목은 서브타입을 못 가려 필수 절 검사가 조용히 빠졌다.

**REST**
| | |
|---|---|
| 항목 패턴 | `(GET|POST|PUT|PATCH|DELETE)/\S+` 예: `GET/api/docs/{docId}` |
| 필수 절 | 규칙 · 에러 · 엔드포인트 · 미결사항 |
| 항목 블록 | 헤딩 + 한 줄 요약 + 화면·유스케이스·서비스 + yaml 조각(그 엔드포인트만) |

**MCP**
| | |
|---|---|
| 항목 패턴 | `[a-z][a-z_]+` 도구명 |
| 필수 절 | 규칙 · 도구 · 에이전트 순서 · 미결사항 |
| 항목 블록 | 헤딩 + json(inputSchema) + 결과 예시 + 에러 표 |

**템플릿은 둘이 따로다**(카드 AG) — `API-REST.md`·`API-MCP.md`. 한 파일에 `## 3. 엔드포인트 (또는 도구)`처럼 괄호로 겸업시켰더니 사람은 읽어도 검사기는 「도구」「에이전트 순서」를 못 찾아, MCP 문서가 템플릿대로 써도 미완성이 됐다. `get_template(…, "API", subtype="MCP")`로 받는다.

지금 REST 문서는 OpenAPI 전체가 코드블록 하나라 엔드포인트가 항목이 아니다. 고쳐야 한다(6장). 공통 `components/schemas`는 `스키마` 절에 두고 항목으로 하지 않는다.

| | |
|---|---|
| 항목 패턴 | `[A-Za-z_]+\.[a-z_]+` 예: `SpecService.save` · `pipeline.save_pipeline` · `queries.document_view` · `git.commit_push` |

[[SYNC-MS-001]]~009를 쓰면서 확정한 구조다. 함수 100개. **MS 문서 하나 = 클래스 명세 4장 절 하나 = 코드 파일 하나.** 크기가 아니라 구조로 나눈다.

### 2.11 CODE — 구현 계획

| | |
|---|---|
| 항목 패턴 | `[A-Z]\d*` 슬라이스 (A 기반 · B1~Bn 시나리오 슬라이스 · C 통합 · D1~Dn 이후 묶음). 글자는 묶음, 숫자는 그 안 순서 |

코드 자체가 아니라 **코드로 가는 계획과 기록**. 커밋은 슬라이스 카드의 `완료` 행에 남는다. 형식은 [[SYNC-STD-004]] 개발 규약.

### 2.12 STD — 표준 (단계 밖)

11단계에 속하지 않는 타입. 명세가 아니라 **명세를 쓰는 법**이다. 프로젝트 산출물이 아니라 플랫폼 자산이므로 대시보드 11칸에 안 나오고, 프로젝트 상세에 "표준" 묶음으로 따로 보인다. 싱크독 프로젝트에만 있고 다른 프로젝트는 싱크독의 STD를 그대로 쓴다 — 저장소 `README.md`가 링크로 가리키고, MCP `get_template`이 본문을 준다.

| | |
|---|---|
| 항목 패턴 | `[A-Z]+-\d+` 또는 `V-[A-Z]+` — 규칙 항목 (`DEV-1`, `V-PRD`) |
| 필수 절 | 미결사항 |
| 권장 절 | 자유 |
| 항목 블록 | 자유 |
| 문서 | `SYNC-STD-001` 명세 작성 규약 (이 문서) · `SYNC-STD-002` 뷰 규약 · `SYNC-STD-003` 체인 지도 · `SYNC-STD-004` 개발 규약 |

필수 절이 `미결사항`뿐인 이유 — 규약은 구조를 강제할 대상이 아니라 강제하는 쪽이라서. 이 문서 자체가 PRD 필수 절을 못 채워 영원히 미완성이 되는 걸 막으려고 타입을 따로 뒀다.

## 3. 규약 위반 — 저장 거부

`validate`(UC-S1)가 검사하는 것 전부. 하나라도 걸리면 `convention-violation`에 `violations[{line, rule, message}]`.

| rule | 검사 |
|---|---|
| `frontmatter.missing` | frontmatter 블록 없음 |
| `frontmatter.field` | 필수 필드(`doc_id` `type` `title` `status`) 없음 |
| `frontmatter.type` | `type`이 11단계 코드 또는 `STD`가 아님 |
| `frontmatter.status` | `status`가 둘 중 하나(`draft`·`approved`) 아님 |
| `frontmatter.doc_id` | 형식 `^[A-Z]{1,4}-[A-Z]+-\d{3}$` 아님, 또는 파일명과 다름, 또는 `type`과 다름 |
| `frontmatter.ref` | `upstream`에 문서 ID 형식 아닌 것 |
| `frontmatter.status_change` | MCP 경로 저장에서 `status`가 현재 DB 값과 다름. 상태 변경은 웹(UC-H8)에서만. GitHub 경로는 검사 안 함 |
| `frontmatter.title.subtype` | 서브타입이 있는 타입(DOM·UI·API)의 `title`에 키워드가 없음 — DOM 「도메인」「클래스」「ERD」(2.6) · UI 「화면 설계」「와이어프레임」(2.7 — 둘 중 어느 것이든 규약은 같고, 검사기가 문서를 찾는 열쇠다) · API 「REST」「MCP」(2.8). 제목으로 서브타입을 가르므로 없으면 항목 패턴도 필수 절도 정하지 못한다 |
| `item.punct` | 항목 ID 뒤에 `.`·`:` |
| `item.duplicate` | 같은 항목 ID가 둘 |
| `item.reused` | 삭제된 항목 ID 재사용 |
| `item.padding` | 번호에 앞자리 0 |
| `item.pattern` | 첫 토큰이 ID처럼 보이는데(`^[A-Z]+-?\d`) 타입 패턴에 안 맞음 — 오타 방지 |
| `ref.format` | `[[ ]]` 안이 `문서ID` · `문서ID#항목ID` · `#항목ID`(같은 문서) 형식 아님. 항목ID는 `\S+` |
| `author.unknown` | GitHub 경로 커밋 작성자가 미등록 (자리표시 User). 저장은 되고 완료만 막힌다 |
| `file.deleted` | GitHub 경로에서 명세 파일이 삭제됨. 문서는 남기고 `draft`로 내리며 항목 전부 `is_deleted`. 파일을 되살리면 풀린다 |

**위반이 아닌 것**: mermaid 문법 오류, 미존재 참조, 필수 절 누락, 빈 항목 블록, 번호 없는 절 헤딩(4장 `section.unnumbered` 경고까지다 — 저장은 된다).

**위반이 아니지만 저장을 막는 것**: DOM 선행조건(2.6) — `precondition-unmet`. `validate`가 아니라 `pipeline`이 생성 때 한 번 본다.

## 4. 미완성 — 경고

저장은 된다. `approved`로 바꿀 때 하나라도 있으면 `status-blocked`(UC-H8 1a에 조건 추가).

**대부분은 `validate`가 본문 하나만 보고 내지만 전부는 아니다.** 문서 하나로 판정할 수 없는 것은 다른 데서 온다 — 어느 것이 그런지는 표 아래 문단에 적었다. `warnings`는 `{rule, message}`를 실어 나르고, 그 모양은 어디서 왔든 같다.

| rule | 검사 | 화면 문구 |
|---|---|---|
| `section.missing` | 타입 필수 절 없음 | `필수 절 없음: {message}` |
| `item.none` | 항목이 하나도 없음 (CODE·STD 제외) | `항목이 하나도 없음` |
| `ref.missing` | 미존재 참조가 있음 | `가리키는 곳이 없는 참조: {message}` |
| `entity.mismatch` | DOM 클래스 명세에서 2장(엔티티)과 4장(설계) mermaid의 같은 클래스 속성이 다름 | `엔티티와 설계 클래스의 속성이 다름: {message}` |
| `section.unnumbered` | **단어형 ID 타입**(DOM·MS·MCP)에서 항목으로 인식되지 않은 헤딩에 번호가 없음 | `번호 없는 절 제목: {message}` |
| `dom.name` | DOM 세 문서의 이름이 어긋남. 클래스가 가리킨 테이블·도메인 항목이 없거나, 어느 클래스도 가리키지 않는 테이블이 있음 | `DOM 세 문서의 이름이 어긋남: {message}` |

**`화면 문구`는 사람에게 보이는 말이다.** `warnings`가 실어 나르는 것은 `{rule, message}`이고 `rule`은 기계가 읽는 ID다. 화면이 그것을 그대로 이으면 `item.none` 같은 것이 배너에 뜬다 — 나머지 화면은 전부 한국어인데 거기만 아니다(#13). 규칙을 새로 만들면 이 열도 함께 채운다. 표에 없는 `rule`이 오면 화면은 `rule` 문자열을 그대로 보여준다 — 규약을 늘렸는데 문구를 안 채운 것이 눈에 띄어야 한다.

mermaid 문법 오류는 서버가 판정할 수 없다(브라우저 렌더링). 뷰가 표시한다.

**`section.unnumbered`를 단어형 타입에만 거는 이유.** 번호를 붙이는 목적은 절 제목이 항목으로
오인되는 걸 막는 것이다(1.6). 그 위험은 영문 단어형 ID를 쓰는 타입에만 있다. 전면 적용하면
UI 항목 블록 안 소제목(`### 배치`·`### 요소`·`### 규칙`·`### 시나리오`)이 대량으로 걸린다 — 규약이
허용한 것들이고, **번호가 없는 것이 정상이다**(2.7). 검사기가 "직전 항목보다 깊은 레벨이면 블록 내부"를 판정할 수 있게 되면 그때
넓힌다.

**`ref.missing`은 `validate`가 내는 게 아니다.** 참조가 살아 있는지는 문서 하나가 아니라
**프로젝트 전체 상태**다 — 상대 문서가 나중에 들어오면 저절로 풀린다(`ReferenceService.resolve_missing`).
게다가 파이프라인에서 참조 추출은 규약 결과 기록보다 **뒤**라, 저장하는 그 시점에는 아직 답이 없다.
그래서 **`documents.incomplete_warnings` 컬럼에 넣지 않고 읽을 때 `references.is_missing`에서 센다.**
읽는 곳은 둘 — 완료 게이트(`pipeline.change_status`)와 UI-5 미완성 배너 4a(`document_view.missing_refs`)이고
둘은 **같은 값**을 본다. 컬럼에 굳혀 두면 상대 문서가 들어와도 그 문서를 다시 저장하기 전까지 낡은 값이 남는다.
대신 **문서 목록의 `미완성` 뱃지에는 안 들어간다** — 목록에서 문서마다 참조를 훑으면 쿼리가 문서 수만큼 늘어난다.
목록에서 끊어진 참조는 UI-4 3.2(끊어진 참조 수 — 같은 `references.is_missing`을 프로젝트 단위로 한 번 센 것)가 말한다.

**`dom.name`은 이름 규칙을 추측하지 않는다.** 클래스 명세가 이미 항목마다
`테이블: [[…]] · 도메인: [[…]]`을 적어 두었다. 그 링크를 정답으로 삼는다. 링크가 없는 클래스는
"테이블 없음"을 선언한 것으로 읽으므로 DTO·열거형이 저절로 걸러진다. 검사는 문서 하나가 아니라
프로젝트 단위라 `validate`가 아니라 `tools/`의 교차 검사기가 한다.
